# saastemlycrm-design-system

The design system (Lit components on daisyUI, Material Design 3 roles), the dashboard app that draws
any Payload project, and the contracts a project implements. It never imports a project:
`golden-sea-payload-config/tests/template.test.ts` enforces that, and that it never names a business.

Entry points (package.json `exports`, TypeScript sources):

- `.`: registers every component. `./styles.css`: the stylesheet.
- `./contracts`: what a project's config uses, all pure (`defineConfig`, field types, `tones`,
  `CollectionSettings`, `widgets()`, the block vocabulary). A project imports only this (and `./payload`).
- `./payload`: pure Payload helpers (`where` matching, `select`/`joins`, errors).
- `./client`: the Payload REST client (`api`); `setBackendReady` for a backend that needs starting.
- `./app`: `startDashboard({ config, seedUsers, ready })` hands a project to the dashboard and starts it.
- `./vite`: `designSystem()`, the Vite plugins an app needs (component stylesheets, Tailwind, layers, icons).

The sections below describe the design system and the app; paths without a package name are in this package.

# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Running Scripts

Run TypeScript and JavaScript files with `vpx <file>`, for example `vpx ./scripts/seed.ts --dry-run`. It handles enums, decorators, JSX, and tsconfig `paths`, so do not add `tsx` or `ts-node` to run scripts. `vpx --watch <file>` reruns the file when a file it uses changes, in place of `tsx watch`. `vp node <file>` runs plain Node.js.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.

# Design system rules

The design system is enforced through the components (`tests/architecture.test.ts` fails otherwise):

- **Only primitives style things** (`src/components/primitives`): padding, spacing, sizes, colours, typography. They expose design tokens as typed, responsive variant properties (`size="sm lg:lg"`, `force-open="lg"`).
- **A primitive is one building block.** It draws its own markup and may borrow another primitive's recipes or icons (`button()`, `iconSvg()`), but it never renders another `ui-*` element. Anything assembled from components is **composed** (`src/components/composed`): the app shell, the appearance controls, the filter builder, the column picker, the model selector, the AI assists and the doc form. Code that isn't a component lives in `src/components/base`, for example the contrast audit, brightness sampling, filter queries and appearance helpers.
- **Pages and composed components** (`src/components/composed`) are assembled from `ui-*` elements only:
  - no `class` / `style`, no DOM styling APIs (`classList`, `.style`, `innerHTML`…), no stylesheets, no `css`/`svg`/`unsafeHTML`;
  - no primitive recipes: import only types (`import type`) and element registrations (`import "…/button.ts"`);
  - templates hold `ui-*` elements plus unstyled inline text (`strong`, `em`, `span`, `br`…), nothing else;
  - attribute values must be the primitive's tokens; the test reads each primitive's variants and checks every literal value.
- **Primitives use theme colours only** (`primary`, `surface-container`…), never the Tailwind palette (`red-400`) or literal colours.
- **Layout is proved, not tested.** Every width-deciding class in the design system comes from the layout algebra (`src/components/primitives/layout/algebra.ts`), and the build refuses one written anywhere else. Each of its bundles keeps one invariant by CSS alone, so any page built from them keeps it too, by induction over the DOM: no screen, data, window width or text size is enumerated, because none can make a difference.
  - **The invariant**, for every box, at any width and any text size: (I1) its content never sticks out of it; (I2) running text gets min(7rem, the room its parent has); (I3) padding never leaves a box's content narrower than min(7rem, the box). 7rem is the readable measure (about 14 characters); it scales with the text (HIG Layout, Dynamic Type: adjacent views "may need to stack vertically"). M3 Lists: the content slot "must be the largest-width slot".
  - **The base fact**: every word can break (`overflow-wrap: anywhere` on the page, `src/index.css`), so nothing is held wide by a long word, a URL or a file name. Columns stay readable through explicit minimums, never word lengths.
  - **The bundles** (each with its one-sentence reason in `algebra.ts`): `row` (always wraps: what doesn't fit goes to the next line), `inlineRow`, `rowFill` (the item that takes the room: never under min(100%, 7rem), else it gets a line of its own), `rowEnd`, `stack`, `gridBase` and `grid.*` (auto-fit, each track at least min(100%, X)), `pairsInline` (label beside value from 24rem), `sidebar`, `inset` / `pad` / `padStart` / `padEnd` (padding that limits itself: `min(p, max(0, (100% − 7rem) / 2))`, so nesting can't squeeze content), `cardInset`, `scrollX` (the only place content may be wider than its box) with `scrolled.*` (a table's or steps' 10rem floor, inside it), `fixed` / `fixedWidth` (leaves of at most 4rem), `text.prose` / `text.label` / `text.line`, `cap`, `floating` (a panel at most the window less 1rem a side), `container` (a size container is always `w-full`: containment sizes it as if empty).
  - **daisyUI's components** keep the invariant through `src/styles/daisy-m3.css`'s layout section (buttons wrap and pad within limits, labels and dividers wrap, fieldsets and fields shrink, a horizontal menu wraps, joined controls wrap, card bodies, dialogs, chat bubbles and accordion titles pad within limits). Only the components it covers are allowed (`DAISY_SAFE` in `vite/layout-proof/check.ts`); steps scroll themselves and tables are always drawn inside `scrollX`.
  - **The check** (`vite/layout-proof/check.ts`, with the class vocabulary in `tokens.ts`), run when each primitive's stylesheet is built (`vite/component-css.ts`), and over every primitive by `tests/layout-proof.test.ts` (`vpx vite/layout-proof/report.ts` lists them all). It reads class strings where they're written (recipes, `class` attributes, `classMap`, inline `style`), removes the algebra bundles it finds (referenced, or written out in a variant value, which must stay literal for responsive variants), and refuses what's left if it can change a width: a raw `flex` / `grid` / direction, padding over 4px, a width or minimum width that can exceed its box, `shrink-0` on something not fixed, text that never wraps without being cut, fixed grid columns (unless behind a container query that gives each 7rem: `@min-[T]:grid-cols-N` with T ≥ 7N + 4(N − 1) rem, checked arithmetically), column spans the same way, a size container without `w-full`, physical `left` / `right` sides (write `start` / `end`, so right to left is right too), an undeclared daisyUI component, or running text (`text-body-*`, `text-title-*`, `text-headline-*`) that doesn't say how it wraps (`text.prose`, `text.label` or `text.line`). Composed components, the app and projects write no classes (`tests/architecture.test.ts`), so they're covered by construction.
  - **The frame** (`layout/frame.ts`) is checked like any primitive. Its geometry (rails, open columns, sheets, edges, the main panel's floor) is the algebra's `frame` bundles, laid out as one grid (`frame.grid`: header, start column, main panel, end column) sized by the frame tokens (`--frame-rail`, `--frame-nav`, `--frame-aside`, `--frame-gap`, `--frame-edge` in `theme.css`), whose room `src/components/base/frame-fit.ts` proves for every window width from 320 to 3840px in every reachable state (`tests/frame-fit.test.ts`); its header and toolbars are wrapping rows like everything else.
  - **What stays assumed**: the CSS facts each bundle rests on (one sentence each in `algebra.ts`), and the global stylesheets (`theme.css`, `index.css`, `daisy-*.css`), which are reviewed, not checked.
  - **A diagnostic, not the safety net**: `<ui-contrast-audit>` (`?audit`, or "Check contrast and layout") still measures the page and every open floating layer at the current width (`src/components/base/layout.ts`, `auditLayers`): anything that escapes its box, truncated text squeezed to almost nothing, text cramped under 7rem, a page that scrolls sideways. Use it to look at a page; the proof is what guarantees it.
- **Glass is for the floating layer only**: sheets, dialogs, menus and other controls that float above content use `liquid-glass` (or `liquid-glass-clear` for small controls), defined in `src/styles/theme.css` (tint, light blur, refraction via the `#liquid-glass-refraction` SVG filter in `index.html`, rim shine, shadow). Tooltips, the snackbar, popovers and pickers already use it through their primitives; `shadow-*` utilities on glass replace only its drop shadow. The app is layered, back to front, as elements in that order (`<ui-frame>`'s `appShellLayer`s, then its regions): the background (a photo, `--app-background`; else the theme's washes); the readability scrims (`frame-scrim`, `appShellLayer`'s `scrim`: anchored to the main window, `--frame-window`, it casts the shell's scrim `--app-scrim` outward as a ring and holds the window's own `--app-window-scrim` inside, so the photo in the window is dimmed only as much as the text on the page plane needs; without anchor positioning one scrim covers both); the chrome's glass (`frame-liquid`: the surface's tint, a blur and a sheen, no refraction, under the header, the rails, the columns and the footer; `<ui-frame>` clips it to everything but the main window); the main window's slab (`frame-matte`: a raised pane of liquid glass the page sits on, the only layer that refracts: it bends the photo itself with its own deep filter, `#frame-glass-refraction` in `index.html`, then frosts it, with a wash of light from the top start; `<ui-frame>` clips it to the main window); and on the slab the page plane (`liquid-glass-well`: a light tint, flat). The slab's glass (`frame-lip`: `appShellLip`, an element over the page in `<ui-frame-main>`, pointer events off) makes it a thick piece of glass laid above the page, its edge a demi bullnose. Where refraction is drawn, its backdrop filter is `#frame-slab-lens` (`index.html`): the slab's height is its own box, blurred, so it rounds over at every edge whatever the window's size; the height's slope (a convolution each way) is the displacement map, so what's under the rounded edge (the page, the photo) bends inwards like through a lens, and a lamp above the top start corner shines on it (specular lighting from a point light on a softer copy of the height, broken up by slow noise and kept faint), so the glint is strongest by that corner, uneven like a real reflection, and fades along the edges; the flat middle is left clear. Everywhere, its rim catches a faint line of light, the slope turning away is shaded, and on the chrome under it its straight side shows as a thin dark line with a contact shadow and a deeper one falling to the bottom. Content scrolling to the window's edge passes under the rounded edge and bends with it. The photo shows through both the shell and the window. The audit counts the frame's own layers (`data-frame-layer`: the chrome's tint and blur for text on the chrome, the slab's for text in the window) and the well's tint, so a scrim adds only what they don't already give. Content surfaces inside it (cards, tables) stay solid, and glass never sits on glass. Over a background image, the app shell picks, by bisection, the lightest scrim for the shell (its header, columns and footer) and then for the window (text on the page plane, such as the page header) at which `<ui-contrast-audit>` finds no failing text over the image, so the photo shows as much as stays readable. Text that fails even with the photo fully covered fails on the scheme's own surface; no scrim can fix it, so it is left out of the bisection rather than pushing the scrim to its maximum. The material already handles light/dark, Reduce transparency, Increase contrast and browsers without `backdrop-filter`. Enforced (`tests/design-roles.test.ts`, "everything that floats is glass"): dropdown panels are always glass and have no solid surface option; every `<select>`'s open list (`::picker(select)`) gets the glass from `daisy-m3.css`, because a utility on `<ui-select>`'s wrapper can't reach it; and any primitive that renders a popover or a `<dialog>` must use the glass.
- **Colour contrast (WCAG AA) is checked**: `tests/contrast.test.ts` checks every colour scheme's ink/fill pairs (the scheme generator, `vite/schemes.ts`, fixes unreadable `*-content` tokens); on screen, the command palette's **"Check contrast and layout"** (or `?audit` in the URL) runs `<ui-contrast-audit>`, which measures every visible text against what's really behind it — glass, tints, and the background image — and outlines failures. Run it in light and dark after visual changes. Rules that keep it green: secondary text is the `on-surface-variant` role (80% of the ink), never fainter; coloured text uses the `*-ink` tokens (`text-success-ink`…, the colour mixed toward the ink), never raw `text-success`; tinted backgrounds take full-strength text. The emphasis surfaces (below, "Colour, type and state roles") are computed in the same test: for every scheme, light and dark, every text role and every tone's ink reads at AA on the inverse and the tinted surface and on each `surface-container-*` step inside them.
- **Icons come from the registry only**: `ICONS` / `iconSvg()` / `<ui-icon name>` in `src/components/primitives/media/icon.ts`, filled with `import x from "~icons/<collection>/<name>"` (unplugin-icons, tree-shaken) from line-md (preferred, animated), material-symbols, devicon or logos. Nothing else draws an `<svg>` (`tests/icons.test.ts`). **Animated icons are paced** (`src/components/base/icon-motion.ts`): line-md's SMIL animations would all start in the frame a page appears, on the main thread. `iconSvg` holds each animated copy at its first moment as it is inserted (`pauseAnimations()`), queues it once it is in view (IntersectionObserver), and a frame-paced consumer starts the oldest two per on-time frame; when frames run late it starts none and lets every icon that has waited 400ms jump to its finished drawing, so the queue catches up while the rest still animate. With Reduce motion every icon shows its finished drawing. The policy (`pace`) is proved over every case by `tests/icon-motion.test.ts`.
- Missing something? Add a variant (or a new primitive) in `src/components/primitives`, not a workaround in the page.

## Which component (M3 and Apple component names in brackets)

Pages say what a thing is, and the primitive decides how it looks. `tests/design-roles.test.ts` ("pages use the semantic components") rejects the hand-built versions listed here.

- **Page top**: `<ui-page-header heading subtitle eyebrow>` with `slot="breadcrumbs"`, `slot="status"` and `slot="actions"` (top app bar; large title). Never `<ui-heading level="1">`. It takes as little height as reads well: the eyebrow, title and subtitle are 4dp apart, and the actions sit at the end of the title's line (HIG Toolbars: the primary action "on the trailing side"); they wrap under the title, at the start, only when the panel can't hold both on one line.
- **Cards**: `<ui-card variant="outlined|filled|elevated" heading subhead .count>` with `slot="trailing"` for tags or actions in the header. Cards have no colour, width or shadow options.
- **Words and numbers on things**: `<ui-tag tone>` is a status or category word ("Overdue"). `<ui-badge .count>` is a number and `<ui-badge dot tone label>` is a dot. A badge never holds a word.
- **Key figures**: `<ui-stat label value note tone href main outlined delta delta-dir delta-tone>`, with `slot="trend"`. In a tile a stat is a tonal cell (a filled surface, no outline), so stats in a tile aren't boxes in a box; `outlined` is for a strip on the page itself (each figure a small card like the tiles around it); `main` tints the one figure its row is about (a `stats` block's first item marked `main`). The label takes two lines before it is cut. `delta` is the change against the previous period ("+21%", "−0.4 d") as a chip with an arrow (`delta-dir`) in the ink of what it means (`delta-tone`): the arrow and the words say it, never the colour alone (WCAG 1.4.1). The sparkline sits at the end of the figure's line, or under it in a narrow cell.
- **Label and value pairs**: `<ui-description-list .items layout="stacked|inline">`. It renders a real `<dl>`.
- **Rows of things**: `<ui-list>` with `<ui-list-item headline supporting overline leading-text trailing-text href selected>` (list). `leading-text` is a time or a date in a fixed leading column (an agenda: what's due, in order); `trailing-text` is a short value (a count, a date) that stays on the headline's line however narrow the row (a widget list item's `value`). Beside either, the headline may take two lines. A table cell's second line is the column's `supporting`, not a hand-built stack. Records in columns by state, moved by dragging, are a `<ui-kanban .columns movable>` (a card's menu goes in its `trailing`).
- **Nothing to show, loading, failed**: `<ui-empty-state heading description icon tone loading>` with `slot="actions"`.
- **Messages**:
  - `<ui-alert tone>` is inline, next to what it's about.
  - The snackbar is for something that just happened: `toast(message, tone?, action?)` shows it on the one `<ui-snackbar>` (bottom centre, glass), in place of the one on screen: M3 allows one snackbar at a time, never stacked, and a newer one may replace an outdated one. `success` (the default) carries a tick, `error` its mark. A message with an action or an error stays until it's used, dismissed or replaced (M3: "Snackbars with actions should remain on the screen until the user takes an action on the snackbar, or dismisses it"), so it has no countdown; a plain one goes after 4 to 10 seconds by its length. An action that takes the thing back is `{ label: "Undo", onClick, undo: true }`: Ctrl / ⌘ + Z runs it too, and Alt + G moves focus to it.
  - A decision is a `<ui-modal confirm-label confirm-tone="error">` (dialog; alert). Its button names the verb ("Delete"), and Cancel is always there.
- **One thing looked at or edited over the page**: `<ui-sheet heading subhead size="md|lg" .open>` with `slot="trailing"` and `slot="actions"` (M3 modal side sheet: from the end side, 400dp or 32rem for a form, detached by 16dp with a 16dp corner, the whole screen on a compact window). Closing asks first: Escape, the scrim and ✕ fire a cancelable `ui-dismiss`, so a page with unsaved changes can ask.
- **Actions**:
  - `<ui-button variant="filled|tonal|outlined|text|elevated" color size="xs|sm|md">`. Use at most one or two filled buttons per view.
  - An icon-only action is `<ui-icon-button label>`. The label is its name and its tooltip.
  - A row of controls over content is a `<ui-toolbar label>`, with `slot="end"` for the trailing group.
  - Menus are `<ui-dropdown .items>` with icons, `checked`, `destructive` and separators.
- **Choosing**:
  - One or several options from a few: `<ui-button-group .options select="single|multi">` (segmented button). Never a colour swap between buttons.
  - A setting that applies at once: `<ui-switch>`. A statement someone confirms: `<ui-checkbox>`.
  - A button that stays on: `<ui-button toggle ?selected>`.
  - Chips: `variant="input"` is a picked value, `variant="filter"` is an active filter.
- **Fields**: every field has a name: `label`, `legend`, `aria-label` or a placeholder. A search is `<ui-search label>`, which has the icon, a clear button and Escape to clear. The header's command-palette trigger is `<ui-search launcher shortcut>`.
- **Amounts and progress**:
  - A measurement ("3 of 5 lines ready", "92% on time") is `<ui-gauge tone heading value-text label>`.
  - `<ui-progress>` is only for work the app is doing now, and it is always primary.
  - A position in a fixed sequence is `<ui-steps current tone>`: earlier steps get a tick, `state: "skipped"` shows a dash, and `supporting` is the small line under a label.
- **Text**: `<ui-text variant="body-md">` and `<ui-heading variant="title-lg">` take type roles, plus `emphasized`. They have no `size` or `weight`.

# Language: English and Arabic (i18n, l10n, accessibility)

The interface runs in one language per page load, chosen by the person (`<ui-appearance
kind="language">`), else the browser's, else English; switching saves it (`localStorage`
`ui-language`) and reloads the page, so a session has one language and one direction, laid out
once. Arabic is right to left. Everything below is checked (`tests/i18n.test.ts`).

- **Interface text is compiled, never written in English in code.** Every word people read or hear
  (template text, `label` / `aria-label` / `title` / `placeholder`, a menu item's label, a toast, an
  error, an empty state) is a message: `m.<key>(inputs)` from `src/i18n/index.ts`. Messages live in
  catalogs, ICU MessageFormat 1, one JSON per language (`messages/en.json` for shared words,
  `messages/primitives/`, `messages/composed/`, `messages/app/` for each part), compiled by Paraglide
  (`vite/i18n.ts`) into typed functions in `src/i18n/paraglide` (committed; `bun run i18n`, `vp dev`
  and `vp build` recompile). Keys are `snake_case`, prefixed with the component or view
  (`doc_form_collapse_all`, `list_view_showing`). A message is a whole sentence with its inputs
  (`"Showing {count} of {total}"`), never words glued together in code, because Arabic orders them
  differently. Counts use plurals (`{count, plural, one {# record} other {# records}}`; Arabic has
  `zero`, `one`, `two`, `few`, `many` and `other`). Every language has every key with the same
  inputs, and the compiled output is current (`catalogProblems`, `staleMessages` in
  `src/testing/i18n.ts`). `literalTexts` (`vite/templates.ts`) finds English left in templates.
- **Payload's text is Payload's shape.** A label, hint, placeholder, option label, action word or
  view title in a project's config may be `{ en, ar }`. The dashboard reads the whole config in the
  page's language once as it starts (`localizeConfig`), and every endpoint answer the same way (an
  endpoint may hand back config text as written), so code reading `c.labels.plural` gets a string.
  Anywhere else, `localize(value)`. The contracts export `localize`, `localizeConfig`,
  `isLocalized`, `locale()` and `intl`. With `localization`, `fieldProblems` requires every one of
  these texts in every language.
- **One build per language.** A project's build can be one bundle per language
  (`I18N_LOCALE`): `STATIC_LOCALE` (`vite/i18n.ts`) makes every message that language's, so the
  bundler drops the others' words, and `localeText` keeps only that language's words in the
  config's `{ en: …, ar: … }` (as `__lt("…")`, the same shape with one text, so code reading `.en`
  or `.ar` works). Without `I18N_LOCALE` (dev, tests, a backend worker that answers each request in
  its own language) every language is in. Switching language is a reload into the other build.
- **The person's language goes with them** when the project's people have a `language` field: a
  browser where nobody chose one follows theirs at sign-in (`followLanguage`); one where a language
  was chosen keeps it and writes it to their record; every choice is written there before the
  reload (`keepLanguage`).
- **Content is Payload's localization.** Fields marked `localized: true` hold a value per language;
  the API client sends `?locale=` (the interface's language) on every request, so they are read,
  filtered, sorted and written in it, falling back to English (`mock-runner` implements Payload's
  semantics).
- **Numbers and dates** go through `intl` (`src/i18n/index.ts`): cached `Intl` formatters for the
  language (`intl.number`, `intl.date`, `intl.relative`, `intl.list`, `intl.plural`,
  `intl.collator` for sorting and comparing text). Never `toLocaleString("en-US")` or a fixed
  `"en-GB"`. Arabic writes Latin digits (`ar-u-nu-latn`), so tabular figures line up and a tile's
  build-time size holds. `formatNumber` (units, money, compact) is already localized.
- **Direction is logical.** Layout uses `start` / `end` (the layout proof refuses `left` / `right`),
  so right to left needs nothing per component. Icons that point a way (chevrons, arrows, "back",
  "next") mirror in right to left; marks that don't (a check, a logo, media controls' play) don't.
  Arrow keys follow the reading direction: in right to left, ArrowRight goes to the previous item
  (roving focus, sliders, carousels, tabs, moving a tile with the keyboard).
- **Mixed text is isolated.** A code, a number, an email or an English name inside an Arabic
  sentence goes in its own run (`<bdi>`, or `dir="auto"` on text people typed), so its characters
  don't reorder. A part in another language says so (`lang="en"`), so a screen reader reads it in
  the right voice (WCAG 3.1.2); the page's own `lang` and `dir` are set before the first paint
  (WCAG 3.1.1).
- **Arabic type**: letters join, so it has no tracking (`index.css` sets `letter-spacing: 0` under
  `:lang(ar)`) and no capitals; the system font (Segoe UI, SF Arabic) draws it.
- **Figures keep their place in any language**: a `figures` widget's tiles are keyed by each
  figure's `key` (a stable id) with its words in `label`, and `name(key)` gives a tile's words before
  its data (`Figure`, `src/app/widgets/widget.ts`). A tile keyed by its words would lose its size and
  place when the language changes.

# The project is a Payload config package; this design system draws it

This repository is a template. A new project changes only its config package (`golden-sea-payload-config`: config, endpoints, widgets, seed, and `public/` for its photos and icons) and its app joins the packages (`golden-sea-payload-config/app/main.ts`, `vite.config.ts`: `designSystem()`, `mockBackend({ config, seed })`, `startDashboard`); the design system, the agent and the mock backend stay as they are. `golden-sea-payload-config/tests/template.test.ts` fails when the design system or the backend imports another package or names the business, or when the project imports more of the design system than its pure contracts or defines a custom element: UI is always a block or a design-system component.

- **`golden-sea-payload-config`, the project:** only Payload concepts: the data model (`collections`, `globals`, `config.ts`), the business logic (`endpoints`, which return data, never UI), the screens (`widgets`) and the seed data.
- **`src/app`, the dashboard:** the shell, the generated list and edit pages, the widget host, the assistant and the tours. It reads everything from the config.
- **`src/components` and `src/styles`, the design system.** `src/agent`: the AI runtime.
- **`mock-runner`, the in-browser backend:** the service worker, the Payload-compatible engine, its Vite plugin (`mock-runner/vite`) and a test harness (`mock-runner/testing`); an app hands it a config and seed. It has its own copy of Payload's query semantics; Golden Sea's `tests/payload-parity.test.ts` checks it agrees with this package's `./payload`. The REST client is this package's `./client`, the config types and helpers are `./contracts`, the screen checks `./testing`.

**Data widgets read the Payload config** (`records`, `metrics`, `breakdown`, `counts`, `fields` in `src/app/widgets/data.ts`). A project declares them with no code at all, and they take their meaning from the collection, so the business logic lives with the collection:

- **What a value means comes from its field:** its label; a select's options and their tones (`custom.tones`); a number's format (`custom.number`, written `formats.money("currency")` for money in the currency the document holds, `formats.money("USD")`, `formats.percent()` or `formats.days()`); a date with no time of day reads as the day. A value's tone can depend on its document (`custom.toneWhen`: the first `{ when, tone }` rule that holds), a cell can link elsewhere (`custom.href`, with `$row.…`), and a number can draw as a bar (`custom.gauge`: of a fixed `max` or another field's value).
- **Values worked out on read** are fields with Payload's `virtual: true` and an `afterRead` hook. They are never stored, are shown like any field, and can't be queried, as in Payload. A widget filters on them with `keep` (a `where` matched on the documents as read), after fetching them all.
- **Columns** are field names or dotted paths through relationships and groups (`customer.contactRule`, `eInvoice.status`), labelled by the last field's label, or by `labels`.
- **Actions are declared once on the collection** (`custom.actions`, `CollectionAction`): an `Action` with `when` (a `where` matched on the document as read) and `roles`. Its strings may hold `$row.<path>` (`$row.id`, `$row.customer.name`, `$row.reminder.body`). They show on every matching document wherever the collection's records appear: the last column of a table, an entry's buttons, a list item's. `each` repeats an action once per row of an array field (`$item.…`, `$index`; `itemWhen` picks the rows). An array field's own `custom.actions` act on its rows (`$row` is the row, `$parent` the document). `links()` keeps a whole-segment placeholder as it is, so `link.doc("cases", "$row.case")` works in an action.
- `records`: a table, a list, entries or a timeline (`layout`), with `where`, `sort` (by a virtual field too: then every document is fetched and sorted as read), `limit`, `supporting` (a second line under a column), `labels`, `more` and `empty` (what it says with no rows). Its rows are a collection's documents, or the rows of an array field of a global (`global` and `field`) or of the screen's document (`doc: true` and `field`). A list item can have `tags` (fields, each in its tone) and a `dot`, and `select` makes it a master: picking an item sets a screen parameter that a detail widget's query reads. An entry can have `tags`, `facts` (label and value), `notes` (an array or text field, one line each) and a `notice` (a field, in its tone). A timeline reads its first column as the time, its second as the heading, `text` and a toned `dot`.
- `metrics`: one tile per figure, either a count or the `sum` of a number field (a fixed-currency one, for money). Its `tone` can depend on whether there are any (`{ some: "error", none: "success" }`). A `note` may hold `$count` and `$sum`. A sum of money in each document's own currency shows that currency when every document shares it.
- `breakdown`: a chart of documents grouped `by` a field (a select in its option order, a relationship by title, a date by `bucket`: day, week or month). It counts or adds up `sum`, with one stacked series per value of `stack`, and `as: "table"` gives the same numbers as a table with totals. `sort: "value"` puts the largest groups first.
- `fields`: a document's fields by name or dotted path, with the document's actions under them (`actions: false` leaves them out).
- **Relative dates** in any widget query: `$today`, `$today-30d`, `$today+2w`, counted from the project's `admin.custom.today` (a demo set on a fixed day), else the real day.

`tests/data-widgets.test.ts` checks these against a small project config. For the collection actions it checks every role against every document: each action shows on exactly the documents and roles it names, with its `$row` values filled in.

**Widget kinds** (`src/app/widgets/kinds.ts`, exported from `./contracts`) are the reusable widgets a project builds screens from, each named for what it draws and knowing no business: `chart`, `table`, `list`, `entries`, `stats`, `details`, `gauges`, `steps`, `timeline`, `gantt`, `text`, `message`, `tiles`, `form`, `document`, `settings`, `ask`, `attach`, `alert`, `actions`, `empty`, `custom`, plus `assists` (several on-device AI assists in one tile), `figures` (one tile per figure, `widget.ts`) and `header` (a screen's header from data). A project's config feeds each one:

- `data`: a Payload query, typed by what it answers. Use `query.find<T>(collection, { where, sort, limit, depth, select })`, `query.count`, `query.doc`, `query.global`, `query.endpoint<T>(path)` for an aggregate endpoint, or `query.all({ … })` for several at once.
- `format(data, scope)`: the business logic. It returns the kind's data: its block's fields (`KindData<"chart">` is `ViewBlocks["chart"]` without `type`). It may also return the slots every kind has, drawn in fixed places: `note` and `tags` above, then `choice` (one or several) and `alerts`, the content, then `actions` under it, and `head` (the card's count, tags, actions, subhead). It returns nothing to draw nothing.
- `kind.each({ items, key, title, format(item) })` makes one tile per item.

A kind is an ordinary `Widget` (its `render` draws the slots around its block), so the board, the skeletons, the agent tools and the design check treat it like any other. A widget that would show two main things (steps and details) is two widgets.

**Screens are widgets.** A screen is a list of widgets placed in one of Payload's component slots with `widgets({ header, params, widgets })` (`src/app/widgets/widget.ts`), which gives Payload's own `{ path, clientProps }` form. They cover Payload's four kinds of admin view:

- **Root views:** `admin.components.views.dashboard` (the home page) and the other root views in `admin.components.views`;
- **Collection views:** a collection's `beforeList` / `afterList`;
- **Document views:** an edit tab in a collection's `admin.components.views.edit`, and a collection's `custom.edit.before` (above the form);
- **Global views:** the same two on a global: an edit tab in its `admin.components.views.edit` (`/globals/<slug>/<tab>`) and its `custom.edit.before` (Golden Sea's approval rules: what those rules govern right now, `golden-sea-payload-config/src/widgets/approval-rules.ts`).

Nothing gets a page of its own.

      On a screen of widgets, cards, rows and the record in focus carry each record's actions (its collection's `custom.actions`, run by the screen, the list reloading after). A record with buttons is a box with its link laid over it, its buttons on top. In a widget's tile the layouts are one "View" menu, and the sort shows only with the filters.

Each screen's widgets live in `golden-sea-payload-config/src/widgets/<screen>.ts`. `<app-widgets>` (`src/app/widgets/host.ts`) draws them.

**Everything is tiles.** One tile is 53 × 56px at the default text size (`--tile-w: 3.3125rem`, `--tile-h: 3.5rem`, so tiles grow with the text size), defined in `src/components/base/tiles.ts` and proved by `tests/tiles.test.ts` for every window width from 320 to 3840px at text sizes 1×, 1.25× and 1.5×. The screen is `columnsFor(width)` tiles across: 6 at 320px (tiles shrink to `width / 6` only when six full ones don't fit), then 2 more each time 2 more fit, so the grid gains a tile on each side and never re-centres by half a tile. What the tiles leave over (under two tiles) goes to the main panel, half either side of the page (`--frame-slack`; the rails meet the screen's edges), and the height past whole tiles is left at the bottom, so every edge in the app is on one grid of equal tiles: the frame, the main panel's page, every board tile. The header is 1 tile high, a closed column (a rail) 1 tile wide, an open column (the navigation, the side panel, their sheets) 4, a content sheet 8 (`floating.sheet`) and a wide one 12 (`floating.sheetWide`). The cell includes the gap: the grid is gapless and each surface sits 4px inside its tiles (`TILE_INSET`, the board's `p-1`). Widgets are sized in tiles, never pixels.

**Everything that floats beside something is placed by Floating UI, one way** (`src/components/base/floating.ts`, on `@floating-ui/dom`): a field's help, every dropdown and menu, a combobox's list, a tile's menu, a chart's tip and every tooltip.

- **The panel is a Popover API popover:** the top layer, so no scrolling box clips it; Escape and a click outside close it; focus goes back to its trigger. Put `${floating({ placement })}` on it; its anchor is the button whose `popovertarget` names it, or `anchor()`.
- **Where:** its `placement` (`top-start`, `bottom-end`…), `gap` px off its anchor. With no room there it flips to the opposite side, then to its `fallbacks`; it shifts along its side to stay 8px inside the window, and hides while its anchor is scrolled out of sight. While open, `autoUpdate` keeps it beside its anchor through scrolling, resizing and layout shifts. Closed, nothing runs.
- **Size:** `--float-max-w` / `--float-max-h` are the room on its side and `--anchor-w` its anchor's width, which `floatingHeight.list` and `floating.anchor` read.
- **Motion:** `floatMotion` in the algebra. It grows from the edge touching its anchor (`--float-origin`) on M3's enter and exit, and isn't displayed while closed.
- **Defaults:** help above (a field's "?"); lists and menus under their trigger (a dropdown's `side` / `align`, responsive); a tile's menu 20px above its grip; a chart's tip beside the x.
- **Tooltips:** any element with `data-tip` gets the page's one plain tip, on `data-tip-side`. It shows after a moment from the pointer, at once from the keyboard, and never on touch. `<ui-tooltip variant="rich">` has its own panel, which stays open while the pointer or focus is in it.
- **Not Floating UI's:** the snackbar (a fixed spot on the screen), a tile held in a drag (it follows the pointer), the native select's picker (the browser places it) and the menu's sliding highlight (in-flow layout).
- Floating UI positions only; its accessibility hooks are React's. Here, the Popover API (top layer, light dismiss, Escape, focus return) and each primitive's ARIA (`menu`, `listbox`, `tooltip`, `aria-expanded`) do that part.
- `tests/floating.test.ts` fails CSS anchor positioning on a panel, daisyUI's dropdown or tooltip classes, and a primitive with a popover that Floating UI doesn't place.

**Floating surfaces and primitives are tiles too** (`floating`, `floatingFit`, `floatingHeight`, `tiles`, `tileCap` in the layout algebra). Each outer box is whole tiles across and quarter tiles down. Paddings and gaps inside keep their own spacing. Anchored overlays follow what opened them (CSS anchor positioning, in the top layer), not the grid.

- **Across:** a panel is N whole tiles, at most the window's whole tiles less 1rem each side (`round(down, 100vw − 2rem, --tile-w)`). Menus are 4 (the dropdown's `panel-width` is a tile count: 4, 5, 6), dialogs 10, `wide` 18, the command palette 12, sheets 8 and 12, the assistant 8, a coachmark 7. Content-sized ones (tooltips, a chart's tooltip, the snackbar) are their content's width rounded up to whole tiles (`calc-size(max-content, round(up, size, --tile-w))`), at most 6 (11 for the snackbar). A combobox's list is its field's width rounded up, at least 4.
- **Down:** a panel is its content's height rounded up to quarter tiles (`floatingHeight.fit`). Max heights round down to quarter tiles, select pickers are 2, 3, 4 or 6 tiles, and the snackbar is at least 1 tile.
- **In flow:** form controls (`64`, `xs`–`lg`) are 5, 6, 7, 8 and 10 tiles, progress and gauge `xs`–`lg` are 2, 4, 5 and 7, range caps are 6, 7 and 8, and the header's search pill is ¾ tile tall and at most 11 wide. Each is capped at its parent.
- **A chart's tooltip lives in the top layer** (a manual popover Floating UI places beside the hovered column or crosshair, `data-chart-anchor`). It is beside the x on the side with more room and flips if needed, or above a sparkline. A 64px plot no longer squeezes it to a letter a line, and no card clips it.
- **Proof:** `tests/tiles.test.ts` ("floating surfaces are tiles") reads every primitive. A class string that draws a floating surface (`liquid-glass*`, `modal-box`) may set only widths in tiles (`--tile-w`, the frame's `--frame-nav` / `--frame-aside` / `--frame-rail`) or its parent's (`w-full`, `max-w-full`, `max-w-none`, `min-w-0`, `w-auto`). It may set only heights in tiles (`--tile-h`) or its parent's. Its recipe must take a width in tiles. A `calc-size()` fallback sits behind `not-supports-`, so it never competes with the tile rule (a plain `w-max` after it won and left a tooltip 3.81 tiles wide).

**A screen is a board of tiles.** Every widget is a tile on `<ui-board>` (`src/components/primitives/layout/board.ts`), laid out by `src/components/base/board.ts`, proved over finite domains by `tests/board.test.ts`:

- **Tiles across** come from the board's own width (`lanesFor`: its whole tiles, allowing for the browser snapping a tile to 52.9875px), read in its ResizeObserver, never from the grid; its tracks are quarter tiles like the frame's (`board.lanes`: `--board-quarters`, four per tile across; rows a quarter tile high), never shrunk to fit, and a widget spans four tracks per tile each way, so the board's lines are the frame's and round the same way. The main panel has no border and draws no scrollbar (it scrolls by wheel, touch and keyboard), so its content box is exactly its tiles and the board lies on the frame's tile lines. A 390px phone gives the board 5.
- **Sizes:** every widget has a `size` (required by the type): `s` (6 tiles across, about M3's 360dp fixed pane), `m` (12), `l` (18) or `full` (all), never more than the board has (`SIZE_TILES`, `spanOf`); or an exact `width` in tiles, within `minWidth` / `maxWidth`. `tileSizeOf` (`src/app/widgets/tile.ts`, in the contracts) says what content usually needs: `l` for a table, gantt, document, form, settings or message; `m` for a chart, entries, a timeline, tiles, steps, an ask box, 3+ stats; `full` for a choice that steers the screen; else `s`.
- **Widgets are sized in tiles, like Android's app widgets** (developer.android.com/develop/ui/views/appwidgets/layouts: a widget declares its size in launcher cells, `targetCellWidth` × `targetCellHeight`, and the host places it by them, never by its content). Its height is `rows` tiles of 56px (`rowsHeight`), whatever it holds. Every widget declares `rows`, or takes its kind's (`defaultRows`: text 2, figures 3, lists, charts and cards 8, tables and entries 10). It also has bounds someone may resize it within on their board (Android's `minResize…` / `maxResize…`: `minSize` / `maxSize`, `minWidth` / `maxWidth`, `minRows` / `maxRows`). Left out, its kind's (`KIND_BOUNDS`, by its `skeleton`; a collection's list or a form is a table's): a figure 3 to 8 tiles across and 2 to 6 down (past 8 it is a number in a field of nothing), text 4 across and 1 to 6 down, a list 5 and 4 to 20, a card 5 and 3 to 20, entries 6 and 4 to 30, a chart 6 and 4 to 14, a table 8 and 5 to 30; else any width and about half to twice its rows (`boundsOf`). `tests/mini.test.ts` proves, for every kind, size, rows 1 to 40 and own width 1 to 24, that the bounds hold its own size and min ≤ target ≤ max both ways. So the box a tile waits in while loading is the box it shows its data in: data arriving moves nothing.
- **Everything on a screen is a widget, and every widget a tile:**
  - The screen's header is a `header` widget (`{ header: ViewHeader | { source, render } }`), a bare tile with its own size, `rows` and bounds like any widget. Fixed, or from data: it loads through its `source` like a widget's, as a skeleton of the header in its box meanwhile (`AppWidget.#headerTile`, `src/app/widgets/host.ts`).
  - A screen's `header` (with `headerRows`, default 2) is shorthand for one: the first widget, the board's width, key `header`. Put a `header` widget in `widgets` to place, size or bound it otherwise.
  - Nothing is drawn above or around the board. A grid of widgets that loads one by one (`each`) keeps its loading tile's key for its first item, so it's the same tile in the same box.
- **Narrower than designed, what wraps grows** (`rowsAt`): a widget given fewer tiles than its design (its size's, `full` counted as 18) grows by the number of times its width goes into the design's, rounded (17 tiles for 18 grows nothing), at most its `reflow`: text and the header 2, figures 4 (`reflowOf`); lists, tables and charts scroll or scale inside their tile and keep their height. A tile clips what's outside its box (`overflow-clip`).
- **The default layout is an optimum** (`pack` in `src/components/base/pack.ts`), used while nobody has arranged the board by hand (no tile has `at`). It scores any layout λ on a board L tiles across by one cost, compared in order: C(λ) = (G, A + D + E).
  - G is the gaps, L·H − Σ wᵢhᵢ, minimised first.
  - A is the likeness, Σ over pairs k(dᵢⱼ)·[exp(−(ln aᵢ − ln aⱼ)²/2σ²) − ½]. aᵢ is the widget's aspect ratio in px and σ = ln 2/2. Equal shapes add ½ and shapes 2× apart subtract 0.36, so alike neighbours cost and unlike ones earn. Without the −½ (`LIKE`), every neighbour would cost, and the formula would favour stripes, which have few neighbours.
  - k is a diamond, an L1 ball of radius 1 tile: dᵢⱼ is the tiles between the boxes across plus down, plus ½ for a corner-only meeting, and k = max(0, 1 − d). Neighbours sharing an edge weigh 1, corner neighbours ½, boxes apart 0.
  - D is the drift, Σ [(ln wᵢ/wᵢ*)² + (ln hᵢ/hᵢ*)²]/2τ² with τ = ln 2: a widget bent 2× costs ½, one bent 6× costs 3.3.
  - E is the straight seams, Σ over pairs k·eᵢⱼ times `SEAM` (1). eᵢⱼ counts the parallel edges of two neighbours that line up: tops and bottoms when side by side, starts and ends when one is over the other, and 2 at a corner, where four widgets meet in a +. Lines on the board's border count too. So the pieces interlock like a jigsaw rather than lining up in a grid.
  - For every screen, the best layout minimises J = ∫ C(λ_W) dW over window widths W. Each width's layout is chosen on its own, so J is least when each width's term is least, and `pack` solves one lane count at a time.
  - It solves only at whole `s` widths, L = 6, 12, 18 or 24 (`layoutLanes`, `LAYOUT_STEP`), and the board stretches that layout across the band up to the next (`stretch`: each tile edge x goes to round(x · L′ / L)), as gridstack scales its columns. Solved at every lane count, a window narrowed by one 53px tile moved and resized most of a board's tiles; stretched, a tile more or less only widens or narrows tiles, and the arrangement changes only crossing a band. The map is monotone with slope ≥ 1, so no tile narrows, touching tiles still touch, and none overlap: `tests/board.test.ts` proves it for every band and every pair of spans. A tile stretched past its `maxSpan` keeps its `maxSpan`.
- **How `pack` finds it.** First, exactly over band layouts. The widgets stay in their order, in bands; each band is columns from `TEMPLATES` (halves to sixths of the board); each column is a stack of up to 3 widgets, at the heights the columns ask for. The search is dynamic programming over band ends and band layouts, and is exact because the cost adds up band by band and a band touches only the band before it. The old first-fit layout (`place`) is a candidate too. Bands line up their tops, so the result is then improved by moves that keep every widget a rectangle and open no gap. The move that lowers the cost most is made each time, until none does:
  - A seam slide moves a stretch of the line between widgets wherever no widget crosses its ends. The widgets on one side grow by what the others give up.
  - A column drop moves a column that runs straight to the board's bottom down by up to `DROP` rows. The widgets above it and beside it at the bottom grow by as much.
  - A line split inserts d rows at a line, under it along a stretch and over it elsewhere, so one straight line becomes two d rows apart.
  - A skyline search (widgets at the lowest, leftmost point of the board's top edge, a beam of `BEAM` partial layouts) is kept when it scores better.
- **What's proven and what isn't.** The cost falls with every move, so the moves end, at a local optimum of the formula, not the global one. Past the bands, there are too many layouts to search exactly at run time. A board can keep a straight line across its full width whose crossings are all staggered T's: no stretch of it can move without a widget crossing it. `tests/pack.test.ts` lists every band layout for every sequence of up to 3 widgets of 5 kinds on boards 5, 6, 12 and 24 tiles across. It proves the band step equals the least of them, or first fit's cost where that's lower. It proves the final layout costs no more, and that no single move lowers it. For sequences of up to 4 widgets it proves every result is a layout: no overlap, on the board, inside the bounds, in order.
- **Limits on bending.** A widget's bounds (`BoardItem.bounds`, from its `TileBounds`) say how far it may bend. The default layout narrows a widget to at most half its target width. It never gives a widget fewer rows than it asks for at that width, because its content would be cut off. A widget that doesn't ask for the full width never gets it: its top and bottom would be lines across the board that nothing could break. A fixed tile (the header) is the board's width. A tile sized by hand keeps its size.
- **On the board.** The board then pins each tile where `pack` put it, so a tile opened past its rows pushes only what's under it. The first hand arrangement (a move or a resize) keeps every tile's packed place and size (`#keepAll` in `host.ts`). Results are cached by tiles and lanes; a cold solve takes up to about 60ms. The tile set and every tile's size are decided before any data (next rule), so data arriving never packs the board again.
- **Placement keeps every widget its size** (`place` in `src/components/base/board.ts`), like a launcher's grid: a widget is its target width and height in tiles on every board, whether the navigation is open or not. Widgets go in order, each to the first place in reading order (down the rows, across each from the start), at or after the one before it, where all its tiles are free (gridstack's packing, keeping the order). So small widgets after a tall one go one under another in the column beside it, and no widget goes before one ahead of it. Once someone arranges a board by hand, every tile on it is pinned where it is (`at` and `atRow`, `preferences.boards[…].pins`): free placement, gridstack's float. Pinned tiles are placed first, top to bottom, start to end, each exactly where it was put, or pushed down to the first row there where it's free if a tile placed before it is in the way. Nothing floats up: gaps stay where someone left them (`..--..` rather than `....--`, a hole above a tile). The only thing that closes a gap is a row no tile is in at all, which is taken out like a cleared line in Tetris, moving what's under it up together. Tiles that aren't pinned (all of them on a board nobody arranged, or a widget added since) flow as above, after the one before them in the order. `tests/board.test.ts` proves, for every sequence of up to 3 widgets, flowing or put at lanes 0–1 and rows 0, 1 or 3, on boards 1 to 4 lanes wide: no overlaps, nothing past the board, each put tile at exactly its lane, no empty row left, and two put tiles apart in rows never swapped. Then, in order, a widget with a larger `maxWidth` takes the free tiles after it across its rows, and one with a larger `maxRows` the free tiles under it, no lower than the widgets beside it reach; whatever is left stays empty. Only a board narrower than a widget clamps it (its height then follows `rowsAt`), and a `full` widget is by definition the board's width, so give each widget of a strip an exact `width` (the home figures: four widgets of 5 tiles, one per figure). Only sizes, bounds, `reflow` and order go in. `tests/board.test.ts` proves, for every sequence of up to 5 widgets 1 to 3 tiles wide and 1 to 3 high, some with bounds, on boards 1 to 4 tiles wide: each at the first place, at or after the one before it, where its target fits among the earlier widgets (no earlier place fits), inside the board, none overlapping, each exactly its target size (or `rowsAt`'s) and stretched only within its bounds and never past its neighbours, and none moved by a later widget.
- **Arranging never reloads; loading never blanks.** A page widget's spec is filled in afresh on every render, so the host hands the list or form the same object while its content is the same (`AppWidget.#same`): moving or resizing tiles re-renders the board but never reloads them. A collection list is stale-while-revalidate: rows already fetched for the exact query this session (`listCache` in `list-view.ts`) show at once, the rows on screen stay while a request runs (a new filter, a reload after an action), the answer replaces them only if it differs, and the skeleton shows only when there's nothing to show yet; a different collection starts empty.
- **Every widget keeps to its tile.** The board's cell clips what's in it; a tile with a surface is a card exactly its cell's box (less the 4px inset), its body capped under its header with "Show all" for the rest; a bare tile is a column that clips, its content taking what's left of the box; and a figure that is a widget of its own (`figures`, an untitled `counts`) is drawn as one `<ui-stat fill>`, its card the whole tile whatever it holds. `tests/tiles.test.ts` ("every widget keeps to its tile") pins those rules in the recipes.
- **Empty tiles are allowed; resized widgets are not.** Tiles that no widget's target fills stay empty rather than stretch a widget past its bounds. To fill a row, size or order the widgets so their widths add up on the boards people use (18, 22 and 26 tiles beside a rail or the open navigation), or give the last one in it a `maxWidth`.
- **No stacks: every widget is its own tile.** Short widgets that belong beside a big one (the inbox's reads of a message and its review queue beside the list and the message) are widgets of their own, listed after it: the placement puts them one under another in the column beside it, and each is moved, resized and hidden on its own.
- **Which tiles are there, and their sizes, are decided before the data** (at build time, or from who is looking: `visible(scope)`), so the data never adds, removes, grows or moves a tile, and the skeletons are the screen's final layout (`audit/settle.ts` scores every screen 0):
  - A widget with nothing to show keeps its box and shows its empty state (`empty: { when(data), heading, description }`, an `empty` block). Refused (403), it keeps its box and says so (`denied`, else "You don't have access to this.").
  - An `each` widget declares its tiles (`tiles`, a number or `(scope) => number`); `figures` declare their `labels` (the formatter returns `Figure<L>[]`, so a figure under an undeclared label doesn't type-check). Counts and metrics take their labels from their spec or the field's options.
  - A page's own collection, record or setting is a tile of fixed rows too (below).
  - Nothing measures a tile's content to size it (`fit` is gone; a mini version takes `miniRows`).
  - The screen check (`src/testing/screens.ts`) reports, for every seeded user, a figure under a label it doesn't declare and an `each` with more items than tiles; `screenEmptyStates` lists the tiles that show their empty state, to fill from the seed.
- **Content fits its box:** a tile's body takes what's left of its tiles under its header; what doesn't fit fades out behind "Show all", which asks the board for the rows the whole content needs (`ui-tile-rows`, `rowsFor`) and gives them back on "Show less" (the tiles after it slide). The count of tiles across comes from the board's width (its ResizeObserver), never read back from the grid.
- **One widget, one tile, one card about one thing.** A widget that would draw several cards is several widgets on the same query (identical requests go out once). Figures are widgets too: `figures({ data, format: (d) => [...] })` (`figures` in `widget.ts`) makes one untitled tile per figure (the figure is the card and carries its label; 6 tiles across by default, 4 wide, 3 high; its label is its key on the board), each moved, resized and hidden on its own, all from one request; an untitled `counts` widget does the same, one tile per count (a titled one stays one card). Several items of the same kind, each a card (new suppliers, POs to re-check), are an `each` widget: a tile per item. Order them so rows fill on 18 and 24 tiles across (`l` then `s`, `m` then `s`, `s, s, s`). `grid` and `split` widgets are flattened into tiles (a split's main ones `l`, its side ones `s`, unless they say).
- A widget hidden for the user (`visible`) takes no tile; nothing else removes one.
- **One tile per item** (`each`, `EachSpec` in `widget.ts`): when the number of cards follows the data (an offer comparison per requested line, one card per purchase order), the widget gives `items`, a `key`, a `title` and a `render` per item, and `tiles` (how many, decided before the data) and `empty` (what a tile with no item says). The board gets exactly that many tiles, each the widget's size, loading tiles until the data is in and then each its item in the same key and box (`eachSlots`, `eachTiles`, alike for the host, the agent tools and the design check). Items past the last tile go into the last one, in one card ("2 more", behind its "Show all").
- **Every widget is a `<ui-tile>`** (`src/components/primitives/containers/tile.ts`), the same anatomy everywhere: a header (title, count, `slot="trailing"` for tags, actions and the layout menu), a subhead, the body, and its states (loading: a skeleton of a fixed height for its size; refused and failed: an alert in the body). A titled widget is a surface whose content knows it's in one (`card` blocks become panels, `entries` become rows); an untitled widget is a `bare` tile, only for what steers the screen (a choice, a page-wide alert). A tile is its tiles' size (its width × `rows`): what doesn't fit fades out behind "Show all", which opens it in place. Tiles are dense: 16px padding, an M3 title-medium title, a body-small subhead. The widget's tags, actions and layout menu share one trailing group in the header, there from the first render.
- **One tile can stand out** (`emphasis` on a titled widget, `<ui-tile emphasis>`): `inverse` is M3's inverse surface (dark in a light theme; in a dark theme, where M3's near-white would glare at a tile's size, the surface raised towards the ink with white text), at most one per screen; `tinted` is the primary container with a strengthened ink. Neither is a per-component skin: the surface re-scopes the two colours every role is derived from (`data-surface` on the tile; `surface-inverse` / `surface-tinted` in `src/styles/theme.css`), so every block drawn inside (lists, stats, tags, tables, menus floating out of it) reads its usual roles and stays readable, which `tests/contrast.test.ts` computes for every scheme. A stat's `main` is the same tinted surface.
- **The page** has at least half a tile of room on every side of the main panel (`<ui-container width="full" padding-x="slack" padding-y="half">`): at the sides the slack (`--frame-pad-x`, set by `<ui-frame>`: half of what the tiles leave over, plus half a tile when that's under half a tile), above and below half a tile, so the board stays whole tiles on the frame's quarter lines, and each surface sits 4px inside its tiles. The page's content is at most 24 tiles across (`PAGE_MAX_TILES`, 1272px at the default text size): on a wider main panel the rest is side padding too (the padding is the frame's or half of what's past 24 tiles, whichever is more), so a board has 5 to 24 tiles across on every screen, centred on the frame's half-tile lines. `tests/tiles.test.ts` proves it for every main panel from 320 to 3840px. The window's corner is 16px (`--main-radius`, M3's large shape), inside the half tile of page padding, so it never clips a tile's content.
- **People can arrange their own boards by hand** (`<ui-tile-arrange>` in `primitives/containers/tile.ts` draws the handles and reports; `<app-arrange>` in `host.ts` decides). Every tile has two handles, shown on hover or focus and always on touch screens.
  - **The board holds the tile while it's dragged** (`UiBoard.hold`, `follow`, `drop`; the model is gridstack's). The tile's cell goes into the top layer (a manual popover, `data-held`, the `board.held` bundle), so no scrolling panel clips it and it can be carried anywhere on the screen, over the side panel's Widgets included; it sits at `--lift-x` / `--lift-y` in the viewport at `--held-w` × `--held-h`, registered as not inherited and written straight on the cell, so a pointer move restyles one box and renders nothing. Over another board that would keep it (`carry`, `data-out`) it shrinks to half towards the point it was grabbed by, so the place to let go shows round it. Let go, the attribute comes off (out of the top layer with no hidden frame between, so nothing fades in again) and it springs back into its tiles. It lets the pointer through, so what's under the pointer is the tile it's over. The board is re-arranged live, as gridstack does: each time the place it would land changes, its owner re-places the board (`TileArrange.move` / `place` / `resize`, kept as `live` until `commit` or `cancel`), the other tiles glide out of its way at once (input motion, on the fast spatial spring), and a dashed mark (`boardDrop`, `data-board-drop`, gridstack's placeholder) shows its place and size, gliding with them. Every target is worked out against where the tiles were when the drag began (`placed`, read once at its start; `UiBoard.rectOf` turns a place into px), never where they're gliding to: what's shown is a function of the pointer alone, so tiles making room never pull the target out from under it. The lift is computed from the cell's layout offset, which no transform changes, after every re-place (`updated`, `_slide`), so the tile never shows a frame out of place while the others slide. It stays inside the lanes across. Let go, the board springs it from where it's shown into its place, position and size, as input motion: where it's shown is read the moment it's let go (by the next frame its owner has re-placed it, and its lift, measured from its old place, would show it somewhere it never was), and the board's own slide leaves it alone until its drop animation starts. The tiles the drop pushes aside slide to their new places with it, as the same input motion (not queued after it); the board looks for moved tiles after every render (`updated` calls `_slide`), since a tile pushed down a row keeps its size and no ResizeObserver entry reports it.
  - **The grab bar** on its top edge (M3's 32 × 4dp drag handle) moves it: the point it was grabbed by stays under the pointer, and the board shows live what letting go does. Targets are magnetic, so one holds from a little way off (`#edgesNear`, `#emptySpot` in `host.ts`): over a tile, its edge nearest the pointer (in the tile's own proportions); else any tile's edge within 24px of the pointer (`EDGE_SNAP`); else empty space, where the tile is shown or the nearest free spot within 2 tiles of it (`SPOT_SNAP`; never its own place, which letting go with no target returns it to anyway), or, when none is free, a squeeze: the same dashed outline where the tile is shown, drawn over the tiles it would overlap, and on release the row makes room for it there (`putAt`: tiles before it move back into what room there is, tiles after it move on and wrap, what's still in the way goes down); else the nearest edge within 80px (`EDGE_REACH`). Over another tile, the edge of that tile the pointer is nearest (start, end, top or bottom, in the tile's own proportions) is where it goes in (`TileArrange.move`; the geometry is `insert` in `src/components/base/arrange.ts`), shown at once by the board making room: an edge between two tiles means the same whichever tile's edge it is. Across (a start or end edge), in that tile's row: the tiles from the line on move on along the row, each just clear of the one before it, and one that would pass the board's end wraps, like text, to the start of the next row under the row's tiles; by an end edge, the tiles before the line first move back towards the start into what room there is (never past the board's start or a fixed tile), and only what that room can't hold pushes on. Down (a top or bottom edge), in the lanes it was let go at: by a top edge it goes in at that tile's top and what's under moves down; by a bottom edge the tiles above the line first move up into what room there is (never above the top or a fixed tile), and what that can't hold pushes down, which always has room. Only what's actually in the way moves (`makeRoom`): what the tile lands on moves just clear of it, then what that lands on, each tile always the same way (back or on, set by its first push), so tiles in the same lanes but other rows stay put. Whatever then still lies on another goes down, just under it, the tile put in first (`settle`). `tests/arrange.test.ts` checks the expected cases exactly and, for every row of up to 3 tiles on a 6-lane board with a tile under them and every edge of every tile, that nothing overlaps, nothing leaves the board, and the tile goes in at the line. Over empty space, its tiles go where its top start corner would be (the pointer less where it was grabbed, in whole tiles); it stays exactly there (`place`, `putAt`), and what it lands on goes down. Either way every other tile keeps its place (`#snapshot`: the board's places become everyone's pins) unless it's pushed; in empty space nothing is in the way. Never by a fixed tile or by itself. Reset layout clears the pins. The keyboard's earlier / later trades places with the neighbouring tile. With no target the board shows itself as it was, and letting go there (or Escape) springs it back. Focused: the arrows move it earlier or later, Home to the start, Delete hides it.
  - **The resize corner** at its bottom end resizes it inside its widget's bounds (`minWidth` / `maxWidth`, else its sizes' tiles, and `minRows` / `maxRows`; never past the board's lanes). A widget's bounds always hold its own size (`boundsOf`: its `width` and `rows`, whatever the bounds default to or say), so a tile resized by hand can always go back to the size it was made at: a figure 4 tiles wide isn't held to the 6 tiles of its size once widened. `tests/board.test.ts` ("a widget's bounds") proves it for every size, own width, rows and declared bound below, at and above them. Its start corner stays put and it follows the pointer in px, clamped to those bounds (`--free-w` / `--free-h`, `data-free`); the dashed mark shows the whole tiles and rows nearest that size (`resizeTo`), and the other tiles make room around them live, each time they change. On release it keeps them and springs from the size it was let go at to its place. The corner is the card's own corner traced: as large as the scheme's card radius (`fixed.corner`, at least 20px), on the card's edge with its radius (`rounded-ee-box`). A tile that lifts on hover (a figure that links: `data-tile-lift`) lifts as one piece with its handles (`tileArrange` `lift`), so the corner stays on the card's corner. Focused: the arrows, a tile at a time.
  - **The board waits for the pointer to settle** (gridstack's `pause`): a moved tile's target must hold for `SETTLE_FRAMES` (8) animation frames, about 130ms, before the board re-arranges for it (`#aim`, `#settle` in `host.ts`, counted in frames, never timed), so a tile swept across the board doesn't set every tile it passes moving. Let go before that, it still goes where the pointer aims. Resizing re-arranges at once: its target is a size, not a place the pointer crosses.
  - **Only the corner resizes**: a tile's sides have no handles, so a press near an edge never starts a resize.
  - **Hide** is in the grab bar's popover: a click on the bar (a press that doesn't move; a drag never opens it) opens a small glass popover anchored 20px above it, clear of the tile's edge. It opens on the `click` event, not the pointer's release: `popover="auto"` light-dismisses on a release outside it, and the release that ends the press is one (synthetic events don't trigger light dismiss, so test this with real input) (`tileMenu`, CSS anchor positioning, `popover="auto"` so Escape or a click elsewhere closes it, flipping under the bar where there's no room) with one item, a trash icon and "Remove" (`tileMenuItem`; its accessible name "Remove <tile>"). The tile itself carries no destructive control to brush while scrolling or grabbing it. Delete on the focused bar hides too: the tile goes to the board's hidden tiles ("Show N hidden tiles" brings them back). On a board that keeps widgets from other screens, it removes the kept one.
  - **Compact** (gridstack's `compact()`): on a board arranged by hand, every tile moves up as far as it can in its own lanes, top to bottom, so the gaps people left close and lanes, sizes and the order down each lane stay (`compact` in `src/components/base/arrange.ts`). `tests/arrange.test.ts` proves it over every board of 3 lanes with up to 3 tiles, any one fixed: nothing changes lane or size or goes down, nothing overlaps, a fixed tile stays, the order down shared lanes stays, and no tile can then move up a row.
  - **A hand arrangement follows the board's width** (gridstack's `moveScale`): it's kept with the board's tiles across (`lanes` in the preferences), and on a board of another width every hand-placed tile's start and end edges are scaled (`scaleArranged` in `src/components/base/board.ts`, the map `stretch` uses), rows untouched: on a wider board exactly `stretch`; on one at least half as wide, tiles keep their order across and at least a tile each, and stay apart when they keep a tile of their own (`place` pushes down anything still on another); below half, only the arrangement's order and each width clamped to the board (gridstack's `list` mode). `tests/board.test.ts` proves it for every arrangement width 1 to 24, board width 1 to 30 and tile.
- **Widgets kept in the side panel (drag a tile there).** A tile dragged from a screen's board over another board that keeps widgets (an `<app-widgets board="…">`, the side panel's Widgets) shows a dashed place to let go at the top of that board (`dropTarget`; a `drop` board item: the dashed mark with "+ Keep it here" centred in it), and its own board shows itself as it was; let go there, the widget is kept on that board (`pin`: `preferences.boards[board].added`, its view, `dashboard` or a root view's key, its key on that screen, and for one item of a widget drawn per item that item) and the tile springs back to its place. Only a widget drawn from blocks on a screen with no path parameters can be kept (`pinRefOf`): a collection's list, a document's form, a global and the header stay on their screen. The keeping board finds it again by its view and key (`viewPage`, `widgetAt`: an index into the page's widgets, then `.i` into a grid, `.m i` / `.s i` into a split, `.b i` / `.a i` around a collection's), so it survives a reload, and draws it as its **mini version** (`src/app/widgets/mini.ts`): what it renders, cut to a glance by block kind, so every widget has one. A figure is a **mini figure** (`<ui-stat mini>`, a `stats` block with `mini`), bare, named by the widget's title: its label on one line, then its value with one picture of it taking the rest of that line, the first it has of its sparkline, its share's track or its change chip (its words the picture's accessible name); the note is left out. Under 7rem the picture goes and the value stays on one line. A chart over time is a mini figure of its latest value, the series its sparkline and the change from the point before its delta; bars of categories (no digit in any label) are one share bar of the largest 4 (the rest "Other"); a dial or waffle a figure with its share of the most; a heatmap its total, its weeks the sparkline; a waterfall where it ends against where it starts; a ring, share bar or treemap one share bar. Rows of anything (a table, a list, entries, a timeline, a gantt, tiles) are its first 3 as a list, a line each with its last value at the end (an agenda's time too; dates as "3 Nov"); gauges and facts their first 3; what's for working in the screen (forms, choices, actions, documents, the assistant…) is left out, and a widget left with nothing opens its screen. Every figure of a widget drawn per item is a mini figure too. **A mini version's tile fits what it draws** (the board's `rows: "fit"`, measured, remembered per board), so nothing in it is cut and no room is left over; a mini figure is two tiles. `tests/mini.test.ts` covers each mapping. Inside the side panel the menu sizes only its own rows' icons (`iconSize`: `li > a / button / summary svg`), never a sparkline a widget draws.
  - **The gesture** (`<ui-tile-arrange>`, after interact.js): the pointer is captured, so moves arrive off the small handles; a drag starts only past 4px (`START_DISTANCE`), so a press that doesn't move is a click that focuses the handle for its keys; only the pointer that pressed counts; Escape anywhere cancels (a press never focuses the handle, so the window hears it), as do a lost capture and the tile leaving the page. Near the top or bottom of what scrolls (48px), the drag scrolls it, up to 20px a frame and faster nearer the edge, and reports a move each frame it scrolls (the page moves under a still pointer).
  - What a drag shows is live, kept when the pointer lets go, and put back with Escape. Widths are kept in tiles (`preferences.boards[…].widths`), heights in rows.
  - **The screen's header can't be arranged:** a `header` widget gets no handles. It keeps its place in the order; moves and keyboard steps go around it, and nothing can be dropped in front of it (`#fixed`, `#pinned` in `host.ts`).
  - **A resize is animated:** whenever a tile's tiles change (resized by hand, or re-placed for a new width), the board (`UiBoard._slide`) animates its cell's width and height on the spatial spring, from its old size, or from where an animation in progress has got to, to its new tiles. It compares the placement's tiles (`--span`, `--rows`), never measured sizes, which the animation itself changes. These animations join the slides in the motion queue.
  - Once anything is arranged, a row at the board's end offers "Show N hidden tiles" and "Reset layout".
  - `tests/board.test.ts` ("arranging by hand") proves `resizeTo` stays inside every bound over a finite domain, and that `moveTo` keeps every other tile's order. The choices are saved per screen in `preferences.boards` (the screen's path, a document's id as `:id`); an order applies leniently (a tile added later keeps its place after the one it followed). Only the board's inputs change, so the board's rules still place everything: arranging can't break the layout.
- **A tile's element never moves in the document.** The board draws its tiles in the order they were first drawn (`keepOrder` in `src/components/base/board.ts`): tiles that stay keep their order, new ones go at the end, whatever order they're placed in. Lit's `repeat` moves an element when its items' order changes, and a moved element counts as a new one: its entrance (`@starting-style`, the fade in) plays again and it loses what it was doing (a slide, focus, a scroll). So where a tile shows comes from its placement alone, and every change of place slides; nothing fades but a tile that's new. `tests/board.test.ts` proves it for every order of every subset of 5 tiles, before and after. (The document order is the order tiles were authored and first shown, which is what the keyboard and a screen reader follow.)
- **Nothing jumps: what moves, moves.** A tile whose place changes for any reason (data arriving above it, a tile opening, a resize) slides there on M3's spatial spring, from where it was (its offset, read in the board's ResizeObserver callback, after layout); a tile new to the board, and a tile's content taking its skeleton's place, fade in. A skeleton fills its tiles: the same box as the loaded tile. Every tile holds its skeleton from the first frame, whatever its data turns out to hold. "Show all" sits over the faded end of a capped tile, never in a row of its own, so whether the content overflows can't resize the tile. The main panel always reserves its scrollbar's room (`scrollbar-gutter: stable`), so a page growing past the window doesn't move sideways. A screen header that loads data shows `<ui-page-header loading>` (its lines as skeletons of their real heights), and a menu row whose text changes with the page keeps one line (`oneLine`).
- **Nothing measures itself after rendering.** A component that needs a size (the board's width in tiles, a tile's overflow for "Show all", a chart's axis width) keeps what its `ResizeObserver` reports in its entries (`borderBoxSize` / `contentBoxSize`), computed by the browser in its one layout pass per frame. It never reads `offsetHeight`, `clientWidth`, `scrollHeight`, `getBoundingClientRect` or `getComputedStyle` in `updated()` or right after changing the DOM: each such read lays out the whole page on the spot, and a screen of tiles and charts doing it per component stalled navigation for seconds.
- **Work that bunches up goes through a queue, never a timer** (`src/components/base/work-queue.ts`, proved over every case of 1–3 consumers and 0–6 jobs by `tests/work-queue.test.ts`): `WorkQueue` runs jobs with a fixed number of consumers that give the main thread back with `scheduler.yield()` after each slice of about 8ms (`yieldToMain()`, a MessageChannel message where `scheduler.yield` is missing); `whenIdle(key, fn)` runs `fn` once at background priority (`scheduler.postTask`), however many times it was asked for before it started. No `setTimeout` delays or debounces.
- **First loads draw in turn** (`src/app/widgets/paint-queue.ts`, one consumer on that queue): a widget whose data has arrived for the first time is drawn in page order, so the top of the page shows first and the rest fills in under it. A refresh after an action shows at once, in place.

  - `audit/settle.ts`: for every screen in the navigation, each tile's box when first painted against its box once nothing is loading (layout boxes, without transforms, so motion isn't counted): what moved, grew, shrank, vanished or came late, a cumulative score per screen, and an overlay of the skeleton boxes (red) and the final ones (green) on the final screenshot. A screen whose skeleton is what it settles into scores 0.
  - `audit/motion.ts`: the screencast of each page change and of the columns opening and closing, with every element's box on every frame: jumps (moved or resized more than 4px in one frame with no animation on it or an ancestor), pop-ins (appeared fully visible with no animation), Chrome's layout shifts, a heatmap of the pixels that changed and a strip of the busiest frames.
  - Board tiles carry their key (`data-key`) so the audits can follow a tile from its skeleton to its final state.
- **One queue for motion** (`motion` in `src/components/base/motion-queue.ts`, its policy `plan` proved over every case of a finite domain by `tests/motion-queue.test.ts`). Every animation joins one of three lanes:
  - `input`, the direct answer to a gesture (a column's spring, its menu's fold, a page coming in): it plays at once, and while it plays nothing else starts;
  - `follow`, what follows from it (a board's tiles sliding, one job per board, keyed so a newer move replaces one still waiting): at most `FOLLOW_CONSUMERS` (2) at a time, in arrival order, once no input motion plays;
  - `ambient`, low-stakes motion (a chart's reveal): `AMBIENT_CONSUMERS` (1) at a time, only when no follow motion waits or plays; one that hasn't started and has waited `MAX_WAIT_MS` (250ms) while frames run late (over `ON_TIME_MS`, 25ms) or behind input motion skips to its end.
    A waiting job is held at its first frame, so nothing jumps while it waits. The consumer is paced by animation frames, never by timers.
- **The page moves with a column, and nothing is ever beyond the panel's edge.** While a column opens or closes, the page follows the main panel's edge on every frame. Laying it out again costs about 5ms a frame, now that nothing restyles the whole page (see the next two rules). The springs are input motion. As a spring starts, `<ui-frame-main>` works out how much narrower or wider the page will be once it settles, from where its margins' springs start and end. It reads the springs on the frame after the change, where the style is already up to date (read in the click, `getAnimations` restyled the page once more inside it), and passes what they still have to go. It hands that to its top-level boards (`UiBoard.expectWidth`), which measure their width then (an empty copy of their container in a hidden probe that wide, laid out by the same CSS) rather than take the distance off their own: a page capped at 24 tiles in a wider panel keeps its width, and a board that guessed re-placed every tile mid-spring and back again. Same lanes then as now, nothing is placed at all. A board takes the lanes it will have then at once, and its tiles slide to their new places as input motion on the panel's own spring (what's left of its delay, its duration and its easing, passed with `expectWidth`), so each tile travels once, in one direction, with the edge, and none is ever beyond it. Keeping the old lanes until the spring had settled sent every tile across with the edge, then back across the board.
  Traced at 1914 × 903, opening and closing both columns: no tile was ever past the panel's edge. Before this, opening the side panel left tiles up to 57px beyond it. The navigation's springs run on time (at most one dropped frame). The side panel still costs one long frame on the click (about 55ms): its list of sections and cards is restyled as it goes into and out of its fold, at about 50µs an element, because of the menu recipes' descendant selectors.
- **A column's list never reflows while it springs.** It is laid out at its open width at all times (`frame.listStart` / `listEnd` in the algebra) and the column clips and reveals it, so nothing in it re-wraps and no board in it changes its lanes on any frame; a board keeps its lanes while it isn't laid out (`display: none`). The list settling after the spring (its groups unfolding) is input motion too.
- **A tile that changes size keeps what it holds at its new size while its box springs** (`UiBoard.#play`): its first box is pinned to its new size and the tile clips it, so only the box is laid out on each frame, not its chart, table or text (which reflowed, and redrew from their observers, on every frame).
- **Live backgrounds** (`LIVE_BACKGROUNDS` in `src/components/base/appearance.ts`: `live-waves`, `live-magnet-lines`): animated effects offered in the background picker beside the photos, each tile a live preview (`<ui-choice-tile>` with content). Chosen, `data-background` on <html> names it (index.html sets it before the first paint from `ui-background`), and `<ui-app-shell>` renders it (`liveBackground`, `src/components/composed/actions/live-background.ts`) into `<ui-frame>`'s `background`, the frame's bottom layer, under the glass. The effects are primitives, `<ui-waves>` and `<ui-magnet-lines>` (`src/components/primitives/media/`, ported from React): WebGL 2, one draw call, drawing only while something moves and the area is on screen, still with Reduce motion. They draw in `currentColor` (the page's quiet text colour, read again when the theme or scheme changes: `liveColors`), so they read in light and dark.
- **The glass keeps its refraction at all times, and what of it doesn't depend on the backdrop is drawn once.** The main window's slab refracts the photo (`frame-matte`) and its lip bends what's under its edge (`frame-lip`, `#frame-slab-lens`), both live backdrop filters. The lip's glint (`#frame-slab-glint`, a lamp's highlight broken up by noise) is a layer of its own (`frame-glint`, `appShellGlint`), the viewport's size at the window's top start corner and clipped by the lip, so it is never worked out again with the lens while the window springs or the page scrolls. Measured opening the side panel at 1914 × 903 with refraction on: 23 to 37 frames a second with the glint in the lens, 36 to 41 apart.
- **Values set on a box for that box alone are registered as not inherited.** This covers the board's lanes and each tile's place (`--board-quarters`, `--board-cols`, `--lane`, `--span`, `--row`, `--rows`), the drag's values, and the push delays (`--push-start-delay` / `--push-end-delay`, registered in layout/frame.ts: left unregistered, opening the side panel restyled the whole dashboard, 61ms). An inherited custom property changed on a box restyles everything inside it: the board re-placing its tiles for a new width took 33ms of style, and 2ms registered.
- **A modal opens and closes after the press has painted** (`<ui-modal>`, `<ui-sheet>`, `afterNextPaint` in `src/components/base/work-queue.ts`). `showModal` makes the page behind inert and `close` lifts it, and either restyles every element on the page (about 45 to 90ms on a dashboard, about 28µs an element). In the press's own frame that delayed its answer by as much. Opening, the dialog is shown on the frame after the press; closing, it hides at once (`data-closing`, only the dialog restyles) and `close` runs after that frame. Native `showModal` stays: its focus trap and inert page are the accessibility.
- **The first frame is the settled one.** Nothing that places the page is read from layout while the page is still being drawn, and nothing waits for a ResizeObserver to place what the first frame paints: an observer whose box changed after deeper ones were delivered gets its entry a frame late (Chrome's depth rule, "ResizeObserver loop completed with undelivered notifications"), and that frame is painted. The page's side padding (`--frame-pad-x`) is CSS, from the same `100vw` as the frame's slack. A board's first render holds no tiles: it reads its lanes' width in `updated()` and renders them placed in the same task (`#looked`). A fitting tile's height is remembered across reloads (`ui-board-fit` in localStorage), so a reload packs the board as it was. The app shell's unplaced parts are `display: none` (`index.css`). Reloading the dashboard went from a layout shift of about 1.1 to 0.4 in a slowed browser; what's left is the board packing again as widgets' data comes in.
- **No selector that reads an ancestor's whole `class` attribute** (`vite/scoped-invalidation.ts`, `tests/scoped-invalidation.test.ts`). Chrome can't narrow such a rule to the classes it names, so any class change anywhere restyles everything under the element that changed. daisyUI's button ships one in every sheet that uses `btn`: `[class~="not-prose"] *`, for Tailwind Typography's `.prose`, which the app never uses. With it, a class change on the main panel's box cost 42ms and one on the frame's root 73ms; without it, 0.4ms. The pass drops those selectors from every stylesheet as it's compiled.
- **Style stays scoped: no `:has()` over a large subtree.** A `:has()` whose argument reaches past its subject's children marks every element below "affected by :has()", and any change there makes the browser re-check it: a page coming in under the frame restyled the whole frame, 2,000+ elements per slice of tiles. A primitive's `has-[…]` looks only at direct children (`has-[>…]`), outside one-box components (a kanban card, a table row); state deeper down is a `data-*` flag its component sets (a column's open group: `data-groups-open` on the column, `data-start-groups-open` / `data-end-groups-open` on the frame, from its `<details>`' `toggle` events). daisyUI's whole-document root rules (`themecontroller`, `rootscrolllock`, `rootscrollgutter`) are excluded in `theme.css`. Both are checked by `tests/style-scope.test.ts`.
- **Only what can be seen is built with the page:** a dropdown's items are built the first time it's about to open (pointer on the trigger, focus, or the popover about to show), and a chart's screen-reader table fills its rows at background priority (`whenIdle`) once the page has settled.
- **A page change takes two tasks:** the old page comes down in one, the new one is built in the next (`yieldToMain` between them), then the page transition plays.
- **CSS times are read with `cssTime`** (`src/components/base/css-time.ts`): the build's minifier writes motion tokens in seconds (`.25s`), so `parseFloat` read a 250ms fade as 0.25ms on the built site.
- **Animations stay on the compositor:** only `opacity`, `scale`, `translate` and `rotate` animate continuously or in bulk (chart bars grow by `scale` from their baseline; skeletons pulse their `opacity`). An animation of `height`, `width`, `background-position` or a colour runs on the main thread and restyles or lays out the page on every frame.
- **The frame's background audit runs at background priority** (`whenIdle`), after the frame's own animations have finished, and only when the frame's text, size or theme changed (never just because the page changed).
- **Tiles that move slide:** the board watches its tiles and its width with a ResizeObserver; any change of size is where a move starts (a tile that grew moves the rows under it, the board's width moves everything). In the observer's callback, after layout and before paint, it reads each tile's offset, and a tile that moved slides from where it was (M3's spatial spring; at once with Reduce motion). It counts only its own tiles, never those of a board inside one of them.
- **A collection's list and a document's form are boards too, everything on one board** (drawn by the `collection` and `document` widgets): a collection list is its header, the widgets around it (`beforeList` / `afterList`, boards of their own placed `flush`, so their tiles lie on this one's) and the list, each a `full` tile; a document's edit page is its header (breadcrumbs, title, actions, steps, tabs, problems), its `custom.edit.before` widgets (flush), a bare `l` tile for the form and a bare `s` tile for its sidebar; a custom edit tab is the header with the tabs, then the view (flush). Their heights are `rows: "fit"` (`BoardItem`): the board measures the content as it resizes (`ResizeObserver`, after layout) and gives it the whole tiles that hold it, remembered by `remember` so a return visit starts at that height. A list is the same height loading, loaded, short and empty: the table shows a page of skeleton rows (`skeleton-rows`) and fills a short page with blank rows (`min-rows`), the paging row is always there (the count, rows per page, and the pages as « 1 / n »), and a one-line table's header stays one line (each sort button at least its label and arrow wide; the label cuts with "…" before the arrow wraps).
- **Tile content rules** (`tileProblems` in `src/app/widgets/design-check.ts`, run by `screenDesignProblems` on every drawn tile): no table in an `s` tile; no `grid` or `split` block at a tile's top level (make them tiles); at most 4, 6 or 8 top-level blocks for `s`, `m` and `l` / `full`; an untitled (bare) tile holds only a choice, actions, an alert, a document or a strip of key figures (`stats`: every figure carries its own label), and takes no `emphasis`; at most one inverse tile per screen (`MAX_INVERSE_TILES`; M3's inverse roles are "applied selectively").

**A widget** is a design-system block plus where its data comes from. It loads on its own and shows a skeleton until the data arrives.

- **Sources:** `{ endpoint }` is a GET data endpoint; `{ find }` and `{ count }` are collection queries; `{ doc: true }` is the document of an edit tab; `{ global }` is a global; `{ all }` is several at once.
  - Strings may hold `$doc.id`, `$user.id`, `$user.role` and `$param.<name>`.
  - Identical requests on one screen go out once, so several cards can share one endpoint.
  - A refused source (403) hides its widget, or shows its `denied` text.
- **Drawing:** `render(data, scope)` turns data into blocks (`src/app/widgets/schema.ts`). The blocks are entries, card, heading (a subheading inside a card), grid, split, stats, table, list, details, gauges, steps, chart, alert, empty, tags, actions, choice, timeline, form, attach, settings, tiles, gantt, message, document (a printable document, `ui-document`), ask (questions answered from the records, `ui-ask`) and custom (one of the design system's AI assists, `AssistElement`; build it with `assist(element, key, props)`).
- **The design decisions live in the blocks, not in the screens.** A screen says what to show; the renderers decide how it looks, so a project can't get the hierarchy wrong:
  - **A set of like things is `entries`** (requests, next steps, deliveries): each `Entry` gives its parts (heading, `meta`, `status`, `tags`, `summary`, `text`, `facts`, `people`, `notes`, `notice`, `actions`) and `src/app/widgets/blocks/entries.ts` draws them the same way everywhere. Don't build these from `card` + `text` + `tags` + `actions`. A titled widget whose content is `entries` is drawn as a section (its heading, count and `subhead` over the entries' own cards; `skeleton: "entries"` loads in that shape); with no items it is one quiet line (`empty`).
  - **No cards in cards:** a `card` block drawn inside a card (a titled widget, another card) becomes a filled panel; `entries` inside a card become rows between dividers.
  - **Actions** say what they are, not how they look: `main: true` marks the one primary action (M3: "a single prominent button for the primary action"); a link (`href` only) is drawn as a text button, anything else tonal; `tone: "error"` is destructive and can't be `main` (HIG Buttons; the `Emphasis` type forbids it). `actions` blocks and entries go through `actionBar` (`src/app/widgets/blocks.ts`): links first (past two, the rest in "More"), the main action last, one main at most.
  - **Entries can ask for a file:** `Entry.attach` is an `attach` block's dialog next to the actions (proof of delivery).
  - **A status in a table** (a cell's `dot`) is a tag in its tone: one pill, so the dot and its word never part in a narrow column.
  - **A table's rows are one line** (about 44px): a value that doesn't fit its column ends in "…", and a column's `supporting` key adds the one second line a row may have. A person is a `person` cell (`{ text, person: true }`: their avatar and name; the `records` widget does it for a relationship to a collection people sign in to). A row's own action goes in its last column (a cell's `actions`), and is never drawn filled ("Prominence").
  - **Stats** of 2 to 6 sit in balanced rows (`ui-grid balance`, by the grid's own width): all in one row, or even rows, never one left over (four take one row from 40rem). A `Stat` says how it moved with `delta: { text, dir, good }` (the renderer draws the chip, its arrow and its ink; `good` left out is neutral) and its trend with `trend`. In a titled widget the figures are tonal cells; as an untitled widget (a `full` strip at the top of a screen) each is a small card.
  - **What's due, in order, is a `list` with `lead`** (`ListItem.lead`: "14:00", "17 Nov", "Wed 10:00"): the renderer draws the time column, keeps the supporting text to one line, and ends a row that links somewhere with a chevron (HIG Lists and tables: a disclosure indicator for rows people drill into).
  - **Supporting text** is `note(text)` from the contracts, not a local helper. A `text` block has no size: body text, or `muted` (a note). Subheadings are `heading` blocks, never styled text.
  - **Grids** choose their column width from what's in them (wide for charts, tables, lists, cards, entries; narrow otherwise); cards have no `variant`.
  - **Charts** (`chart` block, `ChartSpec`; `<ui-chart>`): a screen gives the labels, up to six series and the number format; the chart draws the gridlines at round numbers, thins the x labels to what fits, colours the series in the palette's fixed order, and adds the hover and keyboard tooltip, the legend's show / hide chips and the screen-reader table. What a screen may say: `kind` (`line` for a trend, with a soft area under a single series; `bars` for amounts), `stacked` (parts of a whole: stacked bars, or stacked areas for lines), `highlightLast` (bars of one series: the latest in colour with its value, the history muted), `target` + `targetLabel` (a dashed line), and `ranges` (`[{ label: "4 w", points: 4 }, { label: "12 w", points: 12 }]`, with `range` for the one shown first): a segmented switch in the chart's header that cuts every series to its last N points in the browser, so the endpoint sends the longest history once.
  - **Shapes that read at a glance** (each a block, a kind in `kinds.ts` and a primitive in `src/components/primitives/data/`; no `<svg>`, they're HTML and CSS): a **ring** (`ring` block, `ring()`; `<ui-ring>`) is parts of a whole as a donut, a `conic-gradient` masked to a ring, up to six parts in the chart palette's fixed order (a seventh and later fold into "Other" in `chart-muted`), 2px gaps, the total in the middle and the parts listed beside it with their values and shares; with `max`, one reading of a known most (a progress ring). A **funnel** (`funnel` block, `funnel()`; `<ui-funnel>`) is stages in their own order, each a bar in one hue as long as its share of the first, centred, the share that went on between two and the whole funnel's in its caption. A **heatmap** (`heatmap` block, `heatmap()`; `<ui-heatmap>`) is a day per cell, a week a column (`grid.calendar`), each in one hue at four strengths by its amount (an empty day in the highest container colour), with a less-to-more key. All three are alive the same way: pointing at a part, a stage or a day (hover, focus, or a heatmap's arrow keys) brings it forward (the rest fade) and their text reads it (a ring's middle, a heatmap's live line); a part or stage with `href` opens it; they enter with a sweep, bars growing one after the other, or cells coming in a week at a time, handed to the motion queue as ambient motion and absent with Reduce motion. Text stays in text colours; a hue's dot or bar carries identity. No-code: a breakdown with `as: "ring"` draws its groups as a ring (each part opening its documents, `filtered`); counts with `layout: "funnel"` draw their items as stages. Each has a mini version (`mini.ts`): a ring's or funnel's parts as rows, a heatmap as its total.
  - **More shapes, the same way** (block, kind, primitive, mini version; arithmetic in `src/components/base/` with an exhaustive test where there is any):
    - a **bullet** (`bullet`; `<ui-bullet>`) is a figure against its target: a bar over poor, fair and good bands, a tick at the target, `lowerIsBetter` turning the bands round;
    - a **dial** (`dial`; `<ui-dial>`) is one reading on a half ring of toned zones, a needle sweeping to it;
    - a **waffle** (`waffle`; `<ui-waffle>`) is a share as 100 cells, filling in order;
    - a **share bar** (`share`; `<ui-share-bar>`) is parts of a whole as one bar, a legend under it; its line reads the pointed part;
    - a **treemap** (`treemap`; `<ui-treemap>`) is parts sized by value (`squarify`, `tests/treemap.test.ts`);
    - a **waterfall** (`waterfall`; `<ui-waterfall>`) is a bridge: changes rise and fall from the running total, totals stand on zero (`bridge`, `tests/waterfall.test.ts`); with `fit`, the plot spans only the levels it passes through (`bridgeFit`), and a dashed line marks the cut axis, for small changes next to large totals;
    - a **quadrant** (`quadrant`; `<ui-quadrant>`) is items on two measures, split at the medians or at given lines, the corners captioned, `invertY` for a measure where less is better;
    - a **countdown** (`countdown`; `<ui-countdown>`) is deadlines draining live, each from when its clock started (`timeLeft`, `tests/countdown.test.ts`);
    - a **month** (`month`; `<ui-month>`) is a calendar of toned events, a day chosen to list its events (`grid.month`, `tests/month.test.ts`);
    - a **what-if** (`whatif`; `<ui-whatif>`) is sliders and the figures a `compute` function draws from them, recomputed as they move; nothing is saved.
      No-code: a breakdown with `as: "share"` or `as: "treemap"` draws its groups that way (each opening its documents).
  - **Records** (`src/components/primitives/data/record.ts`, one shape `RecordItem`):
    - `<ui-record-cards>`: a card per record, with a monogram, a status stripe and tag, a headline figure, facts and the person on it;
    - `<ui-record-list>`: rich rows, with the facts on the second line so the name keeps its room;
    - `<ui-record-hero>`: one record's summary.
      A monogram's letters (the first two letter-led words) and its chart hue come from the name; a record named by a code (GS-RFQ-0141, INV/2026/0371) takes the monogram of the record it's for (`src/components/base/monogram.ts`; `tests/monogram.test.ts` proves it over every name of up to three words from a fixed alphabet), so a customer has the same colour everywhere. Cards lift on hover and their arrow slides in. Rows take the state layer. Both come in one after the other through the motion queue.
  - **No bare figures.** A figure (a value with a digit; a status in words is exempt) always says something beside its number: a trend (`trend`), a change (`delta`) or its part of a whole or a target (`share`, a bar under it in its tone with its words, `<ui-stat share share-text>`). It holds by construction for the no-code widgets: `counts` draws a tile per value (`figures`), each carrying its share of the whole, and each `metrics` figure carries its share of its collection (the same count or sum over all its records). For figures a formatter makes, the screen check refuses a bare one (`designProblems`: "a bare figure"; tests/design-check.test.ts), so a project can't ship a number in a box.
  - **A figure is a tile.** Figures are widgets of their own (`figures`, `metrics`, `counts`: one tile each), so the board lays them out, moves and resizes them like any tile. A widget never draws several figures inside its own tile: the screen check refuses it ("N figures in one tile", `designProblems`; tests/design-check.test.ts). One-line counters (`size: "sm"`) in a side panel are a list, and exempt.
  - **No empty room under a figure.** A figure that is its own tile (`fill`) draws its trend as a band across the tile's foot that takes the height left over (`statTrendBand`, the chart's `height="fill"`), so a taller tile gets a taller sparkline, never a blank area.
  - **Buttons always look pressable.** A text, outlined or elevated button with no colour takes the primary ink; a tonal one with no colour takes the secondary container. Neither uses the body text colour (`button.ts`). `action()` draws link actions tonal. The AI assist buttons (Translate, "Catch me up") are tonal.
  - **Categories in colour.** A single select that isn't a status (no tones, no status words: a channel, a type) shows as a tag in its option's chart hue (`<ui-tag .hue>`, the option's place in its field, mod 6) in list tables and in `records` cells, so a column of categories isn't grey words.
  - **No plain tables on a page of widgets.** A `collection` widget on any page but its collection's own starts in a visual layout (`list`, `cards`, `board`, `calendar`, `chart`…). People can still switch it to a table. The screen check refuses a table there ("a plain table on a page of widgets", `src/testing/screens.ts`).
  - **Figures count** to their value (`<ui-stat>`, `src/components/base/count-up.ts`): a figure rolls up from 0 as it comes in and from its old value to a new one, keeping its words, decimals and separators (`readFigure`, `figureAt`; `tests/count-up.test.ts` reads back and redraws every figure of a finite domain exactly). A carrier animation of M3's long duration in the motion queue (ambient) paces it, read each animation frame, so the queue can hold it or skip it to its end; none with Reduce motion.
- **The contract types forbid what the design doesn't allow:** icons are `IconName` (`src/components/primitives/media/icon-names.ts`, the list `icon.ts` must cover); stat tones are only `success`, `warning`, `error`; a `Cell` is text, a tag (`tag: true`), a person (`person: true`) or a switch, never a mix; a `Widget` is exactly one kind (`render`, `records`, `counts`, `fields`, `grid` or `split`). A project writes widgets with the kinds (below), never with `render` itself.
- **Links** to the dashboard's pages come from `links()` (`src/app/widgets/links.ts`, in the contracts): `doc(collection, id, tab?)`, `list(collection, filter?)`, `create(collection)`, `global(slug)`, `view(path, query?)`. A project narrows them to its own names (`links<CollectionSlug, GlobalSlug, ViewPath>()`), so a wrong slug doesn't compile; the `no-raw-hrefs` lint rule reports `/collections/…` and `/globals/…` strings built by hand in `src/`; `screenDesignProblems` reports links that lead nowhere (a missing collection, document, edit tab, global or view).
- **Design rules that need data** (`src/app/widgets/design-check.ts`, `designProblems`, pure and in the contracts): button labels of more than four words (M3 Buttons: "ideally 1–3 words"), info alerts with nothing to do (HIG Alerts: make it a `note()`), headings past about two lines, more than six stats, a fact or note said twice in one entry, empty cards, cards three levels deep. `saastemlycrm-design-system/testing` exports `screenDesignProblems({ config, backend, users, password })`, which draws every screen in the config as each user, from any backend that serves Payload's REST API (`ScreenBackend`: `call` and `login`), and runs them; a project calls it in one test (Golden Sea: `tests/design.test.ts`). Each limit cites Material 3 or Apple's HIG; ground new ones the same way (local copies: `material-web/.m3-specs`, `material-web/.apple-specs`).
- **Master–detail:** a list item with `select: { param, value }` sets a screen parameter when clicked and shows selected; detail widgets read it through `$param` (the inbox: the message list sets `?message=`, the reading pane loads `/inbox/message?id=$param.message`).
- **Optional parts of a widget:**
  - `title` makes it a card; `head(data)` gives the card's count, tags and actions.
  - `visible(scope)` shows it by role; `empty` says what it shows when its data has nothing (its box stays).
  - `size` (required) is its tile's size on the board (see "A screen is a board of tiles"); `each` makes one tile per item of its data.
  - `emphasis: "inverse" | "tinted"` gives a titled widget's tile a contrasting surface (one inverse tile per screen).
  - `grid` and `split` group child widgets; the board flattens them into tiles.
- **No-code data widgets:** `records` (a collection as a table or list: `columns` are field names), `counts` (documents per select value, or per `where`, each linking to the filtered list) and `fields` (the document's own fields). Labels, formats, links and tag tones come from the field config.
- **`render`, `head`, `visible` and `empty.when` are pure.** Widget files import only types, `src/app/widgets/schema.ts`, `src/app/widgets/widget.ts` and pure helpers in `golden-sea-payload-config`.
- **Actions are data:** `{ label, call: { path, body }, confirm, fields, prefill, extract, done, reply, assist, print }`. `prefill` fills a field from the server when another changes (an AI-drafted handover note for the person picked); `extract` fills the fields from pasted text or a photo on the device; `reply` shows the endpoint's `message` and goes to its `href`. The host asks, calls (the pressed button is busy, and can't be pressed twice, until the screen shows the result), shows `done` (or the endpoint's `message` with `reply`) in the snackbar, and refreshes every widget in place: each keeps what it shows until its new data is in, and skeletons are for the first load only.
  - **Undo is part of the contract.** An action can be taken back when the server says how: an endpoint's reply may carry `undo: { path, body }` (honoured with or without `reply`; `undo: null` withdraws it), or the action declares `undo` itself when the screen already knows (a switch or a setting: the same call with the value it had). The snackbar then offers **Undo**: it sends that call, says the undo endpoint's `message` (else "Undone"), and refreshes. The endpoint behind an undo checks access as the signed-in user and refuses once what it would take back has been built on; its refusal is what the snackbar says.
  - **Undo or a dialog, never both** (`Reversal` in `schema.ts`; an action that declares `undo` can't `confirm`, by its type). Reversible and internal (a decision recorded, a line moved between states, a setting, a draft removed): it happens at once with Undo, no "are you sure?" (HIG Alerts: "Avoid displaying alerts for common, undoable actions, even when they're destructive"; M3 Snackbar: "To allow users to amend choices, display an 'Undo' action"). Outward or irreversible (an email, order or reminder sent, money paid or recorded, a filing, a deletion): `confirm` naming the verb, and its endpoint answers with no `undo` (HIG Alerts: "when people take an uncommon destructive action that they can't undo, it's important to display an alert"). A dialog that asks for something (`fields`: a reason) is a form, not a confirmation: it stays either way.
  - The AI helper's `call_workflow` gets the same reply, `undo` included, and can call it like any other workflow.
  - A `choice` block sets a URL parameter that sources read through `$param`.
- **Business logic** stays in `golden-sea-payload-config/src/endpoints`. GET endpoints return data for widgets; POST endpoints do the work and check access as the signed-in user. `forward` / `via` (`golden-sea-payload-config/src/endpoints/forward.ts`, `via.ts`) run an existing endpoint as the same request.
- **New block types:** a generic need is a new block: its type goes in `ViewBlocks` in `src/app/widgets/schema.ts` (pure, so the config can use it), and its renderer in `src/app/widgets/blocks/<type>.ts` with `defineBlock`. It holds no project words.
- **No project elements.** Something no block can draw becomes a generic block or a design-system component (composed), never a custom element in `golden-sea-payload-config`. State a screen needs between steps (a drafted RFQ plan) lives on the server, read by widgets like any other data.

**Lint rules.** `lint/index.js` (exported as `saastemlycrm-design-system/lint`) is an oxlint JS plugin named `saastemly`. A project registers it under `lint.jsPlugins` and spreads its `recommended` rules into `lint.rules`, so the editor and `vp check` report these rules. Tests: `tests/lint.test.ts`.

- `prefer-entries`: a grid of cards mapped from a list. Use `block("entries", { items })`.
- `no-local-block-helpers`: a top-level helper that only wraps one `block(...)` call. Use `note(text)` or the block.
- `widgets-are-pure`: in `widgets/`, imports other than the contracts, `/payload`, types and relative files (option `allow`), and `fetch`, `Date.now`, `new Date()`, `Math.random` or browser globals.
- `endpoints-return-data`: in `endpoints/`, importing or calling `block`, `note`, `widget` or `widgets`.
- `no-raw-hrefs`: in `src/`, a `/collections/…` or `/globals/…` string or template. Use the project's `links()` helpers.
- `sentence-case-titles` (warning): a Title Case `title`, `heading` or `label` in a block or widget, or a `subhead`. Option `properNouns`.
- `max-blocks` (warning): a widget `render` returning more than 6 blocks (option `max`). Split the widget or use `entries` or `details`.
- `no-restricted-imports` (oxlint's own): the project imports only `/contracts` and `/payload` of this package, and no Lit.

**The dashboard's own content is data**, editable under Configuration (`golden-sea-payload-config/src/globals/dashboard.ts`, seeded from `golden-sea-payload-config/src/seed`):

All optional: without them the helper uses neutral defaults;

`src/app/site.ts` loads them. Two structural settings stay in the config's `admin.custom`: `nav.groups` (the order and icons of `admin.group`s) and `aside` (the side panel's widgets: widgets like any screen's, `visible` by role, drawn in its Widgets section by `<app-widgets board="aside">` on a board of their own, arranged and remembered on their own; Golden Sea's are `golden-sea-payload-config/src/pages/aside.ts`). `search.synonyms` adds the business's own groups of words that mean the same to the command palette's generic thesaurus (`src/app/command-search.ts`). Notification colours are `custom.tones` on the `notifications.kind` field. Seed globals, and seed fields added to existing globals, are written into existing browsers' data (without overwriting what people set).

## Motion (Material Design 3)

All motion is M3's, from the generated tokens in `src/styles/motion.css` (`vpx vite/motion.ts`); `tests/motion-usage.test.ts` rejects raw durations, delays and curves (`duration-200`, `ease-in-out`, `.2s`, `cubic-bezier(…)`) in primitives and stylesheets.

- **State changes use springs.** This covers hover, press, checked, open/closed, a chevron turning and a section resizing. Colour, opacity and shadow go on `effects`; position, size, rotation and shape go on `spatial`. Use `-fast` for small controls, the default for most things, and `-slow` for full-screen changes. Give each property its own spring, e.g. `[transition:width_var(--duration-spatial-fast)_var(--ease-spatial-fast),background-color_var(--duration-effects-fast)_var(--ease-effects-fast)]`, and chain the steps of a sequence with `delay-(--settle-…)`.
- **Transitions use M3's easing and duration tokens, with no bounce.** A transition is a page changing or a component entering or leaving. Enter on `ease-emphasized-decelerate`. Exit on `ease-emphasized-accelerate`, and quicker. Use `emphasized` for large changes; for example, a FAB opening into a panel is `medium4` on `emphasized`. Use `standard` for small utility motion. Components that appear within the screen (menus, dropdowns, toasts) grow along one axis, away from the edge they're attached to. They don't scale up uniformly. A dialog's fade stays short.
- **daisyUI's own transitions** are retimed in `src/styles/daisy-motion.css`. A primitive's own `transition-*` classes still win over that file.
- **Pages:** `<dashboard-app>` picks the M3 pattern for each navigation and calls `<ui-app-shell>`'s `pageTransition()` (played by `<ui-frame-main>`). The navigation's destinations are `top-level` (a fade). Into a record is `forward` (a slide with a fade), back to its list is `backward`, and another tab of the same record is `lateral` (a slide without a fade).
- **Reduce motion:** the spatial tokens are 0, so nothing slides or scales; fades remain. Add `motion-reduce:` fallbacks for keyframe animations.

## Data tables (collection lists)

Collection lists (`src/app/list-view.ts`) are built on Payload's REST query parameters, which the mock backend implements. `src/payload/select.ts` handles `select`, `populate` and `joins`; `locale` and `fallback-locale` are accepted but do nothing, because no field is localized.

- `<ui-table>`:
  - **Lines:** `lines="one"` (collection lists and widget tables) makes every row one line, 44px tall (Apple HIG's 44pt target; M3's 56dp list item at density −3): a column is as wide as its longest value up to 20rem, past which the value ends in "…" (hovering shows it whole), and the table scrolls sideways when its columns don't fit. A column's `supporting` line is the only second line. The header is a quiet line of small labels, with no band. `lines="wrap"` (the default) wraps values in columns of at least 10rem, for what must be read whole (a printed document's lines). `tests/table-rows.test.ts` reads the row heights from the recipe for every density.
  - **People:** a column's `avatar` puts a 28px avatar (a picture, else initials) before the value; the pair never wraps apart. The list page does it for a relationship to a collection people sign in to.
  - **Sorting:** columns marked `sortable` sort from their header; `sort` holds a Payload sort string and `ui-sort` reports changes. Shift-click sorts by several columns.
  - **Columns:** `align: "end"` right-aligns numbers in tabular figures; `hiddenColumns` hides columns by key.
  - **States:** `loading` dims the current rows, or shows skeleton rows when there are none; `empty` is what shows when there are no rows.
  - **Arranging columns** (opt in with `reorderable` / `resizable`; `columnOrder`, `columnWidths`, `ui-columns` with `{ order, widths }`):
    - Move: drag a header (a mouse moves it after 6px sideways; touch needs a 350ms long press so swipes still scroll). The header lifts to elevation +2 and follows the pointer, the column's cells are tinted, and a primary line down the table shows where it lands. Escape cancels; the click that ends a drag never sorts. Keyboard: Ctrl + Shift + ← / → on a sortable header. A `fixed` column (the record link) stays first, because the whole-row link comes from the first cell.
    - Resize: drag the line on a header's end edge (64–800px), or focus it and use ← / → (Shift: 48px steps). Double-click or Enter fits the column to its content again. A sized column's text ends in "…".
    - Order is applied leniently (`src/components/base/columns.ts`): unknown keys are dropped, and a column added later keeps its place after the column it followed. Header cells are `position: relative` from the base layer (`daisy-m3.css`), so daisyUI's pinned columns stay sticky.
  - **`<ui-column-picker>`** lists the columns in the table's order, with earlier / later arrows (the keyboard and screen-reader way to reorder). Reset restores the default columns and order, and the list page also clears the widths.
- `<ui-filter-builder>`: its fields are typed text, number, date, select (also used for relationships) or boolean. It edits conditions as chips and emits a Payload `where`. The conversion lives in `src/components/base/filter-query.ts`, so pages can build the same `where` from saved conditions.
- `<ui-column-picker>`: the "Columns" checklist, with Reset; it pairs with `hiddenColumns`.
- **List page behaviour:**
  - The table's state lives in the URL (`q`, `sort`, `page`, `limit`, `filters`, `match`, `view`).
  - Table or cards: the cards view shows each record as a card (title, then the visible columns as label and value), with a Sort select in place of the headers. The choice is saved in `preferences.listView`; a `view` in the URL wins.
  - **A record opens in a sheet over the list** (`<ui-sheet>` around `<dashboard-edit-view embedded>`: the record named once, by its own summary (its badge, kind, title, status and links), so the sheet's header is only its tools, an "Open full page" icon and close (`<ui-sheet label>`, no headline); then the record's steps, the edit page's own form with its tabs, its fields under the tab row on the sheet's surface (no box of their own; only the active tab underlined), and Save at its foot), from a table row, a card or a board card. The URL says which (`?open=<id>`): it can be shared, and Back closes it. Escape, the scrim, ✕ and Back ask first when there are unsaved changes (so does a link that leaves the page). A click with a modifier key, "Open full page" and links from elsewhere go to the record's own page (`/collections/<slug>/<id>`), which is unchanged.
  - **The board moves records** (`<ui-kanban movable>`, only for people who may update the collection): a card dragged to another column (mouse or pen after 6px; touch after a 350ms long press; Escape cancels), or sent there from its ⋯ menu ("Move to …", the keyboard way), changes at once, is saved with a PATCH of the board field, and the snackbar says "<title> → <column>" with Undo, which PATCHes it back (Ctrl / ⌘ + Z too). A refused save returns the card and says why. Which column a record is in, and that the opposite move undoes a move, is `src/components/base/kanban.ts`, checked over every case by `tests/kanban.test.ts`.
  - The columns someone picks are saved in `preferences.listColumns`.
  - A select with `custom: tones({ Overdue: "error", … })` shows as a tag in that tone in the table, on cards, on the board and in summaries. Without tones, a single select named `status`, `stage` or `…Status` gets its tone from its words (`statusColor()` in `src/app/shared.ts`): ended grey, problems red, waiting amber, in progress blue, done green. The words are generic; a project adds its own with `admin.custom.statusWords` (Golden Sea's "on board", "customs").
  - Requests ask only for the visible fields (`select`), related titles (`populate`) and join counts (`joins[...][count]`).

## Generated forms (`<ui-doc-form>`, `src/components/composed/forms/doc-form.ts`)

**A record's or a setting's own page** (a `document` / `global` widget, and a `collection` list) is a tile of fixed rows, decided before the record: a collection's list 12 (a toolbar, a page of rows, a pager), a form by its fields (`pageRows` in `host.ts`), or its widget's `rows`; what's past it scrolls inside (`<ui-tile scrolls>`), and someone may size it by hand within its bounds. Where it is (the breadcrumbs, "Read only") leads the page; what to do with it (Delete, Save or Create, and "Unsaved changes") closes it, under the last field.

**Every field owes the person filling it in, and is checked, by construction** (`src/contracts/fields.ts`, `src/testing/mocks.ts`):

- **A hint and a placeholder.** Every shown field has a hint (`admin.description`): one line, at most `MAX_HINT` (120) characters. A "?" beside the label opens it, with the longer story (`custom.about`) under it, in a glass panel above the "?" (under it when there's no room above; the Popover API and Floating UI: an outside click or Escape closes it). Screen readers always hear the hint as the field's description. Every field people type or pick into (text, email, textarea, number, select, relationship) has a placeholder (`admin.placeholder`), an example of a good value. `fieldProblems(config)` lists what's missing. A project's tests require none (`fieldContractProblems` from `saastemlycrm-design-system/testing`, Golden Sea's `tests/fields.test.ts`).
- **A schema.** `zodOf(field)` is the value's zod schema, derived from its Payload settings (type, `required`, `min` / `max`, `minLength` / `maxLength`, `options`, `hasMany`, `minRows` / `maxRows`, nested fields), with its messages in plain words ("At most 120 characters.", "Pick one of the options."). `custom.zod` narrows it further. `zodOfFields` covers a whole document, and `fieldError(field, value)` gives the first problem. The form checks a field against it as it's typed, once it's been changed. An error from the server wins.
- **A mock.** `mockOf` / `mockFields` (testing) draw faker values inside the schema's own bounds, realistic from the field's name (an email, a phone, a company, a vessel, a port, a reference). `custom.mock` gives a field its own. `fieldContractProblems` checks that every seed document and 20 seeded mocks per collection pass their schema. `tests/fields.test.ts` proves 200 seeded mock documents of every field type pass theirs.
- **The most direct input** (`inputOf`; `custom.input` picks another):
  - a select of 2 to 4 short options is a segmented choice (`<ui-button-group>`, its options' tone or hue as dots), up to 8 with `hasMany` are chips, more are a menu;
  - a checkbox is a switch;
  - a whole number range of 3 to 11 steps is a scale (`<ui-scale>`: numbered steps filling in one deepening hue), or stars when it's a rating or score (`<ui-rating>`);
  - a 0 to 1 share, or a percentage with bounds, is a slider with its value in a bubble over the thumb (`<ui-range bubble>`);
  - days are a stepper (`<ui-stepper>`);
  - money is a number with its currency before it;
  - a day, or a day and time, is a date with quick picks and the date said back ("Tue 24 Nov · in 7 days", amber when a deadline has passed: `<ui-date-input>`).
- **One anatomy for every field** (`<ui-field>`): the label, with "Required" until it's filled, a check that pops in once it's good, and the "?". Then the answer, with an accent bar at its start that grows while it has focus. Under it, what's wrong, sliding in with a short shake, and a count against `maxLength` that turns amber near it and red past it. Every motion is on M3's tokens and absent with Reduce motion. Every `<select>` opens its list from the field: it fades and drops in, its options cascade, the chosen one carries the primary check, and the chevron turns.
- **A field shows one of three things:** its placeholder, its value, or a suggestion. Where the browser has the Prompt API (Chrome's on-device model, the downloadable one, or OpenAI with a key in `index.html`), each editable field of the document form that can take one has sparkles beside the "?". These are text, email, paragraph, number, yes/no, date, and single choices and relationships of up to 80 options. A press asks `suggest()` (`src/agent/built-in-ai.ts`) for one answer from what the rest of the document says. The answer is limited to the field's type and options and is null rather than invented (`tests/suggest.test.ts`).
  - The suggestion takes the control's place and size (`layers` in the algebra), dashed in primary, with the sparkles at its start and "Use" at its end.
  - Focus moves to it. A press or Enter takes it and fills the field, which marks the form unsaved. × or Escape leaves it and puts focus back on the sparkles. Typing an answer of one's own clears it.
  - When no answer comes, a line under the field says why.

The forms render every Payload field type (payloadcms.com/docs/fields/overview) and follow the Admin Panel's behaviour:

- **Choices:** select, relationship and upload fields are a `<ui-combobox>`, a searchable picker. It uses chips for `hasMany`, groups polymorphic `relationTo` by collection, and offers an ✕ (`admin.isClearable`; on by default for optional fields). Text and number fields with `hasMany` are combobox chips you type into.
- **Relationships:** the hint line links to "Open" the related document and to create a "+ New" one (`admin.allowEdit` / `admin.allowCreate`). Uploads preview the picked image.
- **Dates:** `admin.date.pickerAppearance` (`dayOnly`, `dayAndTime`, `timeOnly`, `monthOnly`) picks the input, bounded by `minDate` / `maxDate`.
- **Numbers and text:** numbers take `admin.step`. A textarea takes `admin.rows`, and shows a counter with `maxLength`. Code and JSON fields are monospaced. JSON is checked as it's typed and kept as typed until it parses.
- **Arrays and blocks:**
  - Rows collapse (`admin.initCollapsed`), with Collapse all / Expand all.
  - Each row is labelled with its first value ("Line 03 · Lincoln Omnia 46").
  - A ⋯ menu moves, duplicates (below the original) and removes rows (`admin.isSortable`, `minRows` / `maxRows`).
  - Blocks are added from a menu and take an optional block name.
- **Widths:** `admin.width` (`"50%"`, `"20rem"`) sets a field's share of its row (`<ui-box basis grow>` in a wrapping `<ui-flex>`). Fields without a width share what's left equally. A field never gets narrower than 12rem, so rows wrap on a narrow panel. A field with a width outside a row keeps that width.
- **`filterOptions`:**
  - Relationship and upload pickers offer only the related documents matching the `where`, or the `where` a function returns from `{ data, siblingData, id, relationTo, user, req }`.
  - Selects offer the options their function returns.
  - Blocks offer only the slugs their function allows.
  - The current value always stays listed.
  - The mock API enforces the same rules on save (`mock-runner/src/mock/runtime/fields.ts`). For example, Payload's error "This relationship field has the following invalid selections: S1".
- **Layout fields:** a collapsible honours `admin.initCollapsed`. A group with `admin.hideGutter` has no box. Tabs show how many errors they hold.
- **Join fields:** shown as a table of the documents pointing at this one (`admin.defaultColumns`, with a count and "+ Create new"). The page fetches them with `joins`.
- **Errors:** a field with an error turns red, with its message in place. The edit page lists the fields that need attention at the top.
- **Edit page:** Save stays disabled until something changes. Ctrl/⌘ + S saves. Leaving with unsaved changes asks first.

`vite/layer-variants.ts` moves only top-level daisyUI base rules (such as `.input`) to the `components` layer. A rule nested in another (daisyUI's `.mockup-browser-toolbar { .input {…} }`) stays where it is; moving it once gave every input on the page a search icon.

## Colour, type and state roles (Material Design 3, with Apple's guidance)

The roles are in `src/styles/theme.css`, derived from each colour scheme's daisyUI colours. `tests/design-roles.test.ts` rejects raw values in primitives (and the old `size` / `weight` on text in pages). Pick a role by what the thing is, never by how it should look.

- **Ink:**
  - `on-surface` is the main text.
  - `on-surface-variant` is secondary text: supporting lines, captions, header labels and icons. `<ui-text color="muted">` uses it.
  - `on-surface-disabled` (38%) is for disabled content.
  - Never "base-content at 70%".
- **Lines:**
  - `outline` is for boundaries people must find: text fields, selects, checkboxes and radios. It's at least 3:1 against the surface (WCAG 1.4.11). Hovered, fields darken to `on-surface-variant`.
  - `outline-variant` is decorative: dividers, card, table and chip borders.
  - `daisy-m3.css` maps daisyUI's own field and divider lines onto these roles.
- **Surfaces** (separation by tone first, shadows only for what floats):
  - `surface` is the base.
  - `surface-container-lowest` → `-low` (cards, table header bands) → `surface-container` (navigation, grouped sections) → `-high` (dialogs, hovered rows) → `-highest` (filled fields, code).
  - The steps are larger in dark themes.
- **Containers:** `primary-container`, `success-container` and the like are tinted fills, each paired with an `on-*-container` ink. Selected rows, list items, chips and the active navigation item use `primary-container`. The colour schemes' `secondary` is often near-white, so M3's secondary-container isn't used for selection.
- **Emphasis surfaces** (`src/styles/theme.css`, set with `data-surface="inverse|tinted"` by the tile and the stat): `--inverse-surface` / `--inverse-on-surface` (M3's inverse roles in a light theme: the ink, deepened, with the surface as its text; in a dark theme the surface raised towards the ink, M3's "surface bright" direction, with white text) and `--tinted-surface` / `--tinted-on-surface` (the primary container and an ink stronger than `on-surface`). They are registered colours computed on the root, and the surface re-scopes `base-100` and `base-content` with them, so every role above is re-derived inside (the inverse surface is a dark region in either theme: `color-scheme: dark`). Don't restyle components for a dark panel; put them on the surface.
- **State layers:**
  - A state layer is a wash of the content's own colour: hover 8%, focus 10%, pressed 10%, dragged 16% (`--state-hover` and the rest).
  - Use the `state-layer` utility on any interactive element; primitives have no hand-made hover fills left, and daisyUI's menu items hover at the same 8%. It's a background-image over the element's own background, applies hover only with a real pointer, focus only for keyboard focus, and nothing when disabled.
  - For a one-off, use the token: `hover:bg-on-surface/(--state-hover)`. Never `hover:bg-primary/12`.
- **Target sizes:** every control is easy to hit whatever it looks like. `touch-target` adds an invisible hit area, centred on the control: at least 48px on touch screens (M3) and 24px with a mouse (WCAG 2.5.8). The control keeps its visual size, so dense layouts stay dense.
  - It's on every `.btn`, the small icon controls (chip remove, combobox clear, sort headers, trace and source rows) and labels that wrap a checkbox, radio or toggle.
  - The rule: anything with `state-layer` also has `touch-target` (`tests/design-roles.test.ts`).
  - It uses `::before`; the table's resize handle draws with `::before`, so it widens itself on touch instead.
- **Density (opt-in):** `<ui-table density="0|-1|-2">` makes each row 4dp shorter per step, with text unchanged (M3 density; `size` scales the text instead); one-line rows go 44, 40, 36px, and at each a row still holds a 32px control. Collection tables offer it as "Row height" (Default, Compact, Dense) in the Columns menu, saved in `preferences.listDensity`.
- **Prominence:** one main action per screen, two at most (Apple HIG; M3's filled button is for the most important action). Every other action is tonal (`variant="soft"`), outlined or plain, and per-item actions in lists are never filled. The screen audit (`?audit`, or "Check colour contrast") counts the visible filled buttons per surface: the page, and each dialog, sheet or popover separately (`src/components/base/prominence.ts`). It outlines the extras in warning colour.
- **Default scheme:** daisyUI's own themes get two fills darkened for AA in `daisy-m3.css` (dark primary, secondary). `tests/contrast.test.ts` checks the default light and dark themes with those overrides.
- **Chart colours:** data series use `chart-1` … `chart-6` in that fixed order (a series keeps its slot whatever is hidden) and `chart-muted` for the history behind a highlighted bar; never a status colour (success, warning and error keep their meaning), and text never wears a series colour.
  - They are generated per colour scheme, never hand-set: `vite/chart-colors.ts` derives them from the scheme's own tokens (slot 1 has its hue, the others turn from it by 120° or 180°), and `vpx vite/schemes.ts` writes them into `schemes.css` as `--chart-N: light-dark(for light surfaces, for dark surfaces)`, for the default scheme too. They follow the `color-scheme` of the element that draws with them, so a chart inside `surface-inverse` takes the dark half.
  - `tests/chart-colors.test.ts` proves, for every scheme in light and dark: at least 3:1 (WCAG 1.4.11) against every surface role, and against an emphasis surface, a card and a stat's cell inside one; inside sRGB; neighbouring slots apart for full colour vision and for red-green colour blindness (simulated); and equal to what the generator derives. After changing a surface role, an emphasis surface or a scheme, run `vpx vite/schemes.ts` (then `vp check --fix`).
  - Not covered: a filled panel (`surface-container-high` / `-highest`) inside an emphasis tile, and the swatches in the glass tooltip (the series' names are beside them).
- **Type:** M3's 15 roles. Text is set by role (`<ui-text variant="body-sm">`, `<ui-heading variant="title-lg">`), never by a raw size. Each role brings its size, line height, weight and tracking:
  - `display-*`: big numerals.
  - `headline-*`: page and dialog titles. `<ui-heading variant="page">` is the fluid page title.
  - `title-*`: section, card and item titles.
  - `body-*`: running text, table cells and descriptions.
  - `label-*`: text inside components, such as tags, counts and metadata.
  - `emphasized` is the same role one weight heavier (unread, selected, the key figure).
  - Sizes and line heights are M3's. Weights and tracking follow Apple's advice for system fonts: titles and headlines semibold, labels medium, tracking only on small labels.
  - Components whose `size` prop is itself a display scale (swap, countdown, text-rotate, diff, avatar initials) are the listed exceptions.

## Elevation, shape and spacing (Material Design 3)

**Focus shows the way a control is used, never as a ring around it.** `src/styles/daisy-m3.css` draws it for every element, so no primitive draws its own:

- **Typing** (a text box, text area, select, combobox, stepper, prompt): the caret, and the field's own edge turning primary at 2px, on any focus. No ring: the caret already says "type here". A bare input inside a box that shows its edge says so (`[--focus:field]`, with `has-[input:focus]:` on the box).
- **Pressing** (a button, chip, tab, row, card, tile, chart mark): keyboard focus only. A 2px primary line just inside the control's edge, following its corners, over its focus state layer. A filled coloured button uses its content colour instead. Being inside, it's never clipped and never touches a neighbour.
- **Choosing** (a checkbox, radio, switch, slider): keyboard focus only. M3's state layer, a soft primary halo 4px around it.
- An element that hands its focus to something else says which (`outline-none` with `[--focus:host]`: the card or row around it shows it; `[--focus:fill]`: its own fill does, like a menu row's tint or a resize handle's bar).

`tests/focus.test.ts` fails a focus outline or ring in a primitive's classes, and an `outline-none` without a reason.

**Nothing is cut by the box it's in, by construction.** A choosing halo (4px out), a selected tile's ring and an elevation-1 shadow paint outside their element, and any ancestor that scrolls cuts them at the edge its content touches, on both axes: a box that scrolls one way clips the other, because CSS turns that axis's `visible` into `auto`.

- Every scroller gives its content a ring's room: 4px on every side. Use the algebra's `scrollRoom` (`inset["1"]` across, `py-1` down). The exception is a box clipped on purpose along the other axis (`overflow-x-hidden` / `-clip`), whose content carries its own margin, like the main panel's page inset.
- A text area's own padding is its room (`[--ring-room:own]`).
- A tile that fits its content (a `[data-fit]` cell) lets its body overflow visibly, so it's measured whole and its last row (Save, Create) is never cut.

- A box that clips without scrolling (`overflow-hidden` / `-clip`) and may hold something focusable uses the algebra's `clipRoom` (`overflow: clip` with a 4px `overflow-clip-margin`), so a ring on its edge is painted whole. Box `overflow="hidden"`, the tile body and the bare tile use it.
- A box that clips only what draws no ring past its edge says why, on itself: `[--clips:<reason>]`. The reasons are `bar` (a track's fill), `shape` (a dial's or treemap's slices), `media` (an avatar or image), `text` (a line's end), `surface` (a dialog, sheet or panel's own corners; its content sits in its padded body), `frame` (the shell's cells, each 4px around its card) and `fold` (a folding menu group, whose rows mark focus with a fill).

`tests/clip-room.test.ts` reads every class string in `src`. It fails a scroller without room, a clipping box with neither room nor a reason, and a reason that isn't on the list.

The tokens are in `src/styles/theme.css`. `tests/m3-tokens.test.ts` rejects anything off the scales in a primitive's classes.

- **Spacing:** M3's dp scale, on a 4px Tailwind unit. The steps are `0.5` (2), `1` (4), `1.5` (6), `2` (8), `2.5` (10), `3` (12), `3.5` (14), `4` (16), `5` (20), `6` (24), `8` (32), `9` (36), `10` (40), `12` (48), `14` (56), `16` (64) and `18` (72). It's in px, so spacing stays the same when text is scaled up. Arbitrary values use the `--space-*` tokens (M3's names, e.g. `--space-300` is 24dp) or a fluid `clamp()`.
- **Shape:** M3's corner scale: `rounded-none`, `-xs` (4), `-sm` (8), `-md` (12), `-lg` (16), `-lg-increased` (20), `-xl` (28), `-xl-increased` (32), `-2xl` (48) and `-full`. The colour scheme's role radii (`rounded-field`, `-box`, `-selector`) are the scheme's choices.
- **Nested corners:** use `rounded-inner` (M3's optical roundness: inner radius = outer radius − padding). A container sets `--outer-radius` and `--outer-padding`. Dropdown panels, combobox lists and menu items already do.
- **Elevation:** `shadow-elevation-1` … `-5` (M3's levels +1 … +5), or `shadow-none`.
  - At rest, use 0 to +3; +4 and +5 are only for hover and drag. Hovered, a component rises one level.
  - Mapping: cards +1 (rising to +2 on hover), menus and popovers +2 (the glass panels' default), dialogs, FABs, snackbars, date pickers and the jump-to-latest button +3, sheets +1 over a scrim.
  - Separation comes from surface tones first. daisyUI's `--depth` is off, so buttons and fields rest at 0.
- **Scrims:** the scrim role at 32%: `bg-scrim/32` (sheet backdrops), dialogs (`src/styles/daisy-m3.css`), and `scrim-cutout` for a spotlight.
- **Shape morph:** M3's shape library has no web version, so morphs are border-radius ones on the expressive springs.
  - Pressed, a button squares its corners (to at most `sm`; a round icon button to `md`) and springs back. A selected round button stays at `md`.
  - `<ui-loading variant="morph">` is M3 Expressive's loading indicator, for page-level waits.
